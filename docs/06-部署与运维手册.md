## 1. 部署形态总览

Knetsec_Ai 是**单进程 + 单文件 SQLite** 的轻量平台，有三种运行方式，任选其一：

| 方式 | 适用场景 | 命令入口 | 面板地址 |
|---|---|---|---|
| 开发模式 | 二次开发、调试 | `npm run dev` | http://127.0.0.1:5173（Vite） |
| 生产模式（推荐） | 日常长期运行 | `npm start` 或 `deploy\scripts\start.ps1` | http://127.0.0.1:8787（server 托管静态） |
| Docker Compose | 需要容器化/迁移机器 | `docker compose up -d --build` | http://127.0.0.1:8000（nginx） |

无论哪种方式，**运行期数据都只在 `data\` 目录**：

```
D:\Knetsec_Ai\data\
├── knetsec.db          # SQLite 主库（WAL 模式，另有 knetsec.db-wal / -shm）
├── .jwt-secret         # JWT 签名密钥（首次启动自动生成，0600）
├── reports\            # 报告落盘：<id>-<type>-<yyyyMMdd>\report.md / report.html
└── logs\               # 启动脚本后台运行时的 stdout/stderr 日志
```

> 备份/迁移 = 复制整个 `data\`；升级 = 替换代码 + `npm install` + `npm run build`（数据不动）。

## 2. 环境要求

| 项目 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| 操作系统 | Windows 10 21H2 | Windows 11 | 全部脚本提供 PowerShell 版本 |
| PowerShell | 5.1（系统自带） | PowerShell 7.x | `install.ps1` / `start.ps1` 兼容两者 |
| Node.js | **24.x**（`>= 22.5` 可用） | 24 LTS | 需要内置 `node:sqlite`、`fetch`、`process.loadEnvFile`；v22.5 起提供 |
| npm | 10.x | 11.x | 随 Node 安装 |
| 磁盘 | 2 GB 可用 | 5 GB | 依赖约 300 MB，数据按条目增长 |
| 内存 | 2 GB | 4 GB | 采集与报告渲染峰值 < 500 MB |
| 网络 | 可访问 GitHub / NVD / CISA / MSRC / arXiv | 配置 GitHub Token | CNVD 需代理，见 §8.2 |
| 可选 | Docker Desktop 4.x | — | 仅容器化部署需要 |

检查环境：

```powershell
node -v        # 期望 v24.x
npm -v         # 期望 10/11.x
powershell -Command $PSVersionTable.PSVersion
```

> **不要使用** Node 20 及以下：`node:sqlite` 在 22.5 才可用；也不要使用需要 Visual Studio 编译工具的原生模块方案。

## 3. 安装步骤（Windows 本机）

### 3.1 一键安装（推荐）

```powershell
cd D:\Knetsec_Ai
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\install.ps1
```

脚本依次完成（幂等，可重复执行）：

1. 检查 `D:\Knetsec_Ai\package.json` 与 Node.js 版本；
2. `npm install`（postinstall 自动构建 `@knetsec/shared`）；
3. 若无 `.env`，由 `.env.example` 复制生成；
4. 创建 `data\`、`data\reports\`、`data\logs\`；
5. `npm run build` 构建 shared + server + web；
6. 可选：注册「登录时自动启动」计划任务（`-CreateScheduledTask`）。

### 3.2 手动安装（等价步骤）

```powershell
cd D:\Knetsec_Ai
npm install
Copy-Item .env.example .env
New-Item -ItemType Directory -Force -Path data, data\reports, data\logs | Out-Null
npm run build
```

首次 `npm install` 约 1-3 分钟；若卡在下载，可临时切换镜像：

```powershell
npm config set registry https://registry.npmmirror.com
```

### 3.3 首次启动与初始化

```powershell
npm start
```

启动过程会自动完成（无需手动建库）：

1. 创建 `data\` 目录与 `data/.jwt-secret`（若未配置 `KNETSEC_JWT_SECRET`）；
2. 打开 `data\knetsec.db` 并开启 WAL 模式；
3. 执行数据库迁移（`schema_migrations` 记录版本）；
4. 写入种子数据：默认管理员、默认数据源、默认系统设置（已存在则跳过）；
5. 启动调度器（`KNETSEC_SCHEDULER=on` 时）；
6. 监听 `127.0.0.1:8787`。

浏览器访问 **http://127.0.0.1:8787**，默认账号 `admin / admin123`（可用 `ADMIN_USERNAME`/`ADMIN_PASSWORD` 覆盖），**登录后立即修改密码**。

## 4. 环境变量（`.env` 逐项说明）

服务端启动时通过 `process.loadEnvFile` 读取**仓库根目录**的 `.env`（不存在则只用系统环境变量）。`.env` 已加入 `.gitignore`，不会入库。

| 变量 | 默认值 | 作用 | 何时修改 |
|---|---|---|---|
| `KNETSEC_HOST` | `127.0.0.1` | 监听地址 | 仅容器/反代内部需要改 `0.0.0.0`，**不要直接暴露公网** |
| `KNETSEC_PORT` | `8787` | 服务端口 | 端口冲突时改；前端开发代理固定指向 8787，改了需同步 `vite.config.ts` |
| `NODE_ENV` | `development` | 运行环境 | 生产设为 `production`（日志改 JSON、关闭 pino-pretty） |
| `ADMIN_USERNAME` | `admin` | 首次启动创建的管理员用户名 | 首次部署前设置；库已存在则不再生效 |
| `ADMIN_PASSWORD` | `admin123` | 首次管理员密码 | **首次部署前务必改**；库已存在则不再生效（改密请用面板） |
| `KNETSEC_DATA_DIR` | `<仓库根>\data` | 数据目录（库/报告/日志/密钥） | 数据盘迁移或多实例时；相对路径按仓库根解析 |
| `KNETSEC_SCHEDULER` | `on` | 是否启用内置调度器 | `off` = 只允许手动采集（调试或外部调度时） |
| `GITHUB_TOKEN` | 空 | GitHub API Token | **强烈建议配置**：未认证 60 次/小时 → 认证 5000 次/小时 |
| `NVD_API_KEY` | 空 | NVD API Key | 可选：5 次/30 秒 → 50 次/30 秒，显著加快采集 |
| `KNETSEC_HTTP_PROXY` | 空 | HTTP(S) 代理地址 | 访问 CNVD/CNNVD 或受限网络时，如 `http://127.0.0.1:7890`；未设时回退 `HTTPS_PROXY` |
| `KNETSEC_JWT_SECRET` | 空 | JWT 签名密钥（≥16 字符） | 多实例/固定密钥时设置；留空自动生成到 `data/.jwt-secret` |
| `KNETSEC_JWT_TTL` | `43200` | Token 有效期（秒，默认 12h） | 安全要求更高时缩短 |
| `KNETSEC_CORS_ORIGINS` | `http://127.0.0.1:5173,http://localhost:5173` | 允许跨域来源（逗号分隔） | 开发用；生产同源部署一般无需改 |
| `LOG_LEVEL` | 开发 `debug` / 生产 `info` | 日志级别 | 排障时临时 `debug` |

> **LLM 配置不在 .env**：LLM 摘要开关、Base URL、API Key、模型名都在管理面板「系统设置」中保存到数据库（`settings` 表），默认关闭。
> `.env.example` 中出现的 `KNETSEC_LLM_*` 四项为预留占位，**当前版本服务端未读取**；配置 LLM 请直接用面板设置。

配置示例（生产）：

```ini
KNETSEC_HOST=127.0.0.1
KNETSEC_PORT=8787
NODE_ENV=production
ADMIN_USERNAME=admin
ADMIN_PASSWORD=请改成强密码
KNETSEC_DATA_DIR=D:\Knetsec_Ai\data
KNETSEC_SCHEDULER=on
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
NVD_API_KEY=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
# KNETSEC_HTTP_PROXY=http://127.0.0.1:7890
# KNETSEC_JWT_SECRET=请填入至少16位随机字符串
LOG_LEVEL=info
```

修改 `.env` 后**必须重启进程**才生效；面板中可修改的设置（关键词、报告章节、通知、LLM、保留天数）保存即生效，无需重启。

## 5. 启动、停止与构建

### 5.1 npm 脚本（根目录 `package.json`）

| 命令 | 作用 |
|---|---|
| `npm run dev` | 同时启动 server:8787（tsx watch）与 web:5173（Vite），统一转发日志与退出 |
| `npm run dev:server` | 只启动服务端热重载 |
| `npm run dev:web` | 只启动 Vite |
| `npm run build` | 依次构建 shared → server → web |
| `npm start` | 生产启动：`node apps/server/dist/index.js`（**需先 build**） |
| `npm test` | 服务端 Vitest 单测/集成测试 |
| `npm run typecheck` | shared + server + web 类型检查 |
| `npm run seed` | 手动执行种子（幂等，调试用） |
| `npm run verify:sources` | 实测全部数据源可达性，输出报告 |
| `npm run smoke` | 端到端冒烟：登录 → 采集 → 查询 → 生成报告 |
| `npm run format` / `npm run lint` | Prettier 格式化 / ESLint 检查 |

### 5.2 部署脚本（`deploy\scripts\`）

```powershell
# 生产模式前台运行（Ctrl+C 停止，自动打开浏览器）
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1

# 生产模式后台运行（日志写 data\logs\server.stdout.log 与 server.stderr.log）
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Background

# 停止监听 8787 的 Knetsec 进程
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Stop

# 指定端口 / 不打开浏览器
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Port 8899 -NoBrowser

# 开发模式
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Mode dev
```

`start.ps1` 启动前会检查：`node_modules` 是否存在、`.env` 是否存在（缺失自动生成）、端口是否被占用、生产构建产物是否齐全；启动后轮询 `/health` 直到通过（30 秒超时）再提示地址。

### 5.3 手动快速试跑（不碰生产实例）

```powershell
cd D:\Knetsec_Ai
$env:KNETSEC_PORT = '8899'
$env:KNETSEC_DATA_DIR = 'D:\Knetsec_Ai\data-test'

# 另开窗口验证后 Ctrl+C，并删除 data-test
```

## 6. 健康检查与版本确认

```powershell
# 健康检查（公开，含数据库连通性）
Invoke-RestMethod http://127.0.0.1:8787/health

# 登录获取 token
$body = @{ username = 'admin'; password = 'admin123' } | ConvertTo-Json
$login = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8787/api/v1/auth/login -Body $body -ContentType 'application/json'
$token = $login.data.token

# 系统信息（需登录）
Invoke-RestMethod http://127.0.0.1:8787/api/v1/system/info -Headers @{ Authorization = "Bearer $token" }
```

健康检查返回 `status=ok` 且 HTTP 200 视为正常；数据库异常时接口返回 5xx（当前为 500），应优先检查磁盘权限与库文件。

## 7. 备份与恢复（SQLite + WAL）

### 7.1 备份原则

- 全部状态都在 `data\`：`knetsec.db`、`-wal`、`-shm`、`.jwt-secret`、`reports\`；
- **WAL 模式下不能只复制 `knetsec.db`**：未 checkpoint 的事务在 `-wal` 文件里，单独复制会丢数据；
- 最稳妥：**停止进程后整体复制 `data\`**；不能停机时，至少同时复制 `.db`、`.db-wal`、`.db-shm` 三个文件（并接受极小概率的不一致）。

### 7.2 停机备份（推荐）

```powershell
cd D:\Knetsec_Ai

# 1) 停止服务
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Stop

# 2) 整目录备份（时间戳命名）
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$target = "D:\Backup\Knetsec_Ai-$stamp"
New-Item -ItemType Directory -Force -Path $target | Out-Null
Copy-Item -Recurse -Force .\data\* $target

# 3) 重新启动
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Background

# 4) 校验备份
Get-ChildItem $target | Select-Object Name, Length
```

建议保留策略：每日增量（仅新增报告）+ 每周全量，至少保留最近 4 周。

### 7.3 恢复

```powershell
cd D:\Knetsec_Ai
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Stop

# 先备份当前数据（万一要回退）
Rename-Item .\data "data-broken-$(Get-Date -Format 'yyyyMMdd-HHmmss')"

# 从备份恢复
New-Item -ItemType Directory -Path .\data | Out-Null
Copy-Item -Recurse -Force "D:\Backup\Knetsec_Ai-20261117-120000\*" .\data

powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Background
```

恢复后验证：`/health` 为 ok → 用原账号登录 → 情报列表有数据 → 报告可打开。

### 7.4 迁移到新机器

1. 新机器安装 Node 24 并复制整个仓库（不含 `node_modules` 与 `data` 也可）；
2. `npm install` + `npm run build`；
3. 复制旧机器 `data\` 到新机器同路径（或设置 `KNETSEC_DATA_DIR` 指向它）；
4. 启动并验证。数据库文件跨平台通用。

```powershell
cd D:\Knetsec_Ai
```

## 9. 日志与排障

### 9.1 日志位置

| 日志 | 位置 | 说明 |
|---|---|---|
| 应用日志 | 标准输出（控制台） | pino：开发彩色、生产 JSON；Docker 用 `docker compose logs` |
| 后台运行日志 | `data\logs\server.stdout.log` / `server.stderr.log` | 由 `start.ps1 -Background` 重定向 |
| 采集运行日志 | 面板「采集任务」→ 运行详情 | 落库 `fetch_runs.logs`，逐行含每源结果与 warnings |
| 审计日志 | 面板「审计日志」 | 登录、写操作留痕 |
| 报告文件 | `data\reports\<id>-<type>-<日期>\` | `report.md` / `report.html` |

提升日志级别排障：

```powershell
$env:LOG_LEVEL = 'debug'   # 或写进 .env 后重启
```

### 9.2 常见问题速查

#### 9.2.1 端口被占用（8787 / 5173）

```powershell
# 查看占用者
Get-NetTCPConnection -LocalPort 8787 -State Listen | Select-Object LocalAddress, LocalPort, OwningProcess
Get-Process -Id (Get-NetTCPConnection -LocalPort 8787 -State Listen).OwningProcess

# 用脚本停止 Knetsec 实例
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Stop

# 或临时换端口
powershell -ExecutionPolicy Bypass -File .\deploy\scripts\start.ps1 -Port 8899
```

注意：改 `KNETSEC_PORT` 后，开发模式 Vite 代理仍指向 8787，需同步修改 `apps/web/vite.config.ts`；生产模式无此问题。

#### 9.2.2 CNVD / CNNVD 不可达

现象：运行日志出现 `schannel: CRYPT_E_REVOCATION_OFFLINE` / TLS 握手失败 / 连接超时，源状态 failed。
原因：CNVD 站点对 TLS 证书吊销列表检查严格，部分网络环境无法完成；也可能是目标站点限制。处理：

1. 配置代理（推荐）：
   ```ini
   KNETSEC_HTTP_PROXY=http://127.0.0.1:7890
   ```
   重启后重试「试采」；
2. 若代理仍失败：在面板停用该源（保留登记），不影响其他源；
3. 用 `npm run verify:sources` 确认当前网络下哪些源可达，并把不可达源保持 `enabled=0`。

#### 9.2.3 GitHub 限流（403/429）

现象：GitHub 相关源失败，错误含 `rate limit` / `API rate limit exceeded`。

1. 配置 `GITHUB_TOKEN`（fine-grained 或 classic，只需 public 读取权限），限流从 60 次/小时提升到 5000 次/小时；
2. 调大该源 `interval_minutes`（如 360 → 720），减少请求频率；
3. HTTP 客户端已内置 429/5xx 指数退避，通常下一轮会自动恢复；
4. 检查是否多台机器共用同一 Token（互相挤占额度）。

#### 9.2.4 NVD 超时/限流

现象：`nvd_cve` 源失败或耗时很长，日志含超时或 403/429。

1. 配置 `NVD_API_KEY`（免费申请），限流 5 次/30 秒 → 50 次/30 秒；
2. NVD 单次查询窗口已限制为 7 天，若失败会在下一轮重试；
3. 网络慢时可调大该源采集间隔，或暂时停用 NVD 源，靠 GHSA/CISA 兜底。

#### 9.2.5 面板打不开 / 静态资源 404

- 生产模式确认已 `npm run build`，且 `apps\web\dist\index.html` 存在；
- 直接访问 `/health` 判断服务是否存活；
- 开发模式访问 5173，确认 Vite 是否启动、`/api` 代理是否指向 8787。

#### 9.2.6 登录持续失败

- 确认 `.env` 中 `ADMIN_PASSWORD` 只在**首次建库**时生效；库已存在则改 `.env` 无效，请用面板改密或删除 `data\knetsec.db` 重来（会丢数据）；
- 检查是否触发登录限流（5 次/分/IP），等待 1 分钟；
- 查看审计日志是否有 `login_failed` 记录及 IP。

#### 9.2.7 `database is locked`

- 确认没有同时运行两个服务实例（重复启动会争抢写锁）；
- WAL 与 `busy_timeout=5000` 已内置，短时锁会自动等待；
- 避免在运行中直接用第三方 SQLite 工具长事务写库。

#### 9.2.8 报告无法下载 / 文件缺失

- 下载接口会按数据库内容重建文件，删掉落盘文件不影响下载；
- 若接口报错，查看 `data\reports\` 目录权限与服务端日志。

#### 9.2.9 采集任务长时间停在 running

1. 查看服务端日志是否有「采集任务执行异常」；进程崩溃/被杀会留下 running 记录；
2. 重启服务时会自动把遗留的 running 标记为 failed（避免永久 409）；
3. 若进程仍在跑但上游极慢，等待其超时结束；必要时用 `start.ps1 -Stop` 停止后重启；
4. 面板「采集任务」中该记录的日志末尾通常能定位到具体源与错误。

### 9.3 采集失败的应急处置流程

当某个数据源连续失败时，按以下顺序处理，避免「越修越乱」：

1. **确认影响面**：面板「数据源」看 `lastStatus`/`lastError`，只影响单个源还是整轮采集失败；
2. **试采复现**：点「试采」拿到错误摘要与前 5 条样本，确认是网络、限流还是解析失败；
3. **检查凭据**：GitHub Token 是否过期、NVD Key 是否被限流；代理配置是否生效；
4. **临时降级**：把该源停用（保留登记与历史条目），保证其他源正常采集；
5. **修复后验证**：重新启用并试采成功 → 手动触发一次采集 → 确认运行记录为 success/partial；
6. **记录**：在运维台账记下时间、源、错误、处理方式，便于复盘与升级后回归。

> 原则：**单源失败绝不升级为整轮失败**；采集器已按此设计（partial 状态 + warnings），运维只需要定位到具体源。

   起始于：`D:\Knetsec_Ai`；
5. **条件**：取消「只有在计算机使用交流电源时才启动」；
6. 保存后右键「运行」验证，浏览器访问 http://127.0.0.1:8787。

### 10.3 NSSM（把 Node 注册为 Windows 服务）

适合「无人登录也要跑」的机器：

```powershell
# 1) 下载 nssm 并解压，例如 C:\Tools\nssm\nssm.exe
# 2) 安装服务
C:\Tools\nssm\nssm.exe install Knetsec_Ai "C:\Program Files\nodejs\node.exe" "D:\Knetsec_Ai\apps\server\dist\index.js"
C:\Tools\nssm\nssm.exe set Knetsec_Ai AppDirectory "D:\Knetsec_Ai"
C:\Tools\nssm\nssm.exe set Knetsec_Ai AppEnvironmentExtra NODE_ENV=production KNETSEC_PORT=8787 KNETSEC_HOST=127.0.0.1
C:\Tools\nssm\nssm.exe set Knetsec_Ai AppStdout "D:\Knetsec_Ai\data\logs\server.stdout.log"
C:\Tools\nssm\nssm.exe set Knetsec_Ai AppStderr "D:\Knetsec_Ai\data\logs\server.stderr.log"
C:\Tools\nssm\nssm.exe set Knetsec_Ai Start SERVICE_AUTO_START
C:\Tools\nssm\nssm.exe set Knetsec_Ai AppExit Default Restart
C:\Tools\nssm\nssm.exe start Knetsec_Ai
```

> 使用 NSSM 时 `KNETSEC_DATA_DIR` 等配置既可写进 `.env`（推荐，仓库根），也可通过 `AppEnvironmentExtra` 注入；不要两处冲突。NSSM 方式下升级需先 `nssm stop Knetsec_Ai`。

## 11. 安全加固

按优先级执行（详见《03-总体架构设计》§7）：

### 11.1 账号与密钥

1. 首次登录立即修改 `admin` 密码（≥ 8 位且含字母数字）；不要继续使用 `admin123`；
2. 若使用 `KNETSEC_JWT_SECRET`，使用随机长串（≥ 32 字符）；更换密钥会使所有已登录会话失效（预期行为）；
3. `GITHUB_TOKEN` / `NVD_API_KEY` 只放 `.env` 或系统环境变量，不要写进代码、文档、截图；
4. `.env` 与 `data\` 不得提交 Git（已在 `.gitignore`）。

### 11.2 网络暴露最小化

1. **保持 `KNETSEC_HOST=127.0.0.1`**：只有本机可访问；
2. 需要局域网访问时，用 nginx/Caddy 反向代理并加 TLS，不要直接把 8787 暴露：
   ```nginx
   server {
       listen 443 ssl;
       server_name knetsec.example.com;
       ssl_certificate     C:/certs/knetsec.crt;
       ssl_certificate_key C:/certs/knetsec.key;

       location / {
           proxy_pass http://127.0.0.1:8787;
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto https;
       }
   }
   ```
3. 限制来源 IP（nginx `allow/deny` 或 Windows 防火墙）；
4. 若面板域名与 API 不同源，设置 `KNETSEC_CORS_ORIGINS=https://你的域名`。

### 11.3 防火墙

```powershell
# 默认不开放 8787；如确需局域网访问，仅放行内网网段
New-NetFirewallRule -DisplayName "Knetsec_Ai 8787 (LAN)" -Direction Inbound -Protocol TCP -LocalPort 8787 -RemoteAddress 192.168.1.0/24 -Action Allow
# 查看
Get-NetFirewallRule -DisplayName "Knetsec_Ai*"
```

### 11.4 只读账号（viewer）

v1.0 的 API 只提供登录/改密与业务读写接口，**未开放用户管理接口**；`viewer` 角色在数据模型与鉴权中已支持，但创建 viewer 账号目前需运维通过数据库维护（后续版本将提供用户管理页面）。若必须隔离权限，推荐反向代理层做 IP 白名单，或为只读使用者单独部署一套实例（只读库副本）。

### 11.5 备份与审计

- 每周全量备份 `data\`，异机保存；
- 定期检查「审计日志」是否有异常登录/频繁失败；
- 升级与恢复前必须备份，见 §7。

## 12. Docker Compose 部署

完整说明见 [deploy/README.md](../deploy/README.md)，此处给出运维视角的命令。

### 12.1 启动

```powershell
cd D:\Knetsec_Ai\deploy
Copy-Item .env.example .env       # 首次：改管理员密码/Token
docker compose up -d --build
docker compose ps
```

访问 http://127.0.0.1:8000（`WEB_PORT` 可改）。数据在 `D:\Knetsec_Ai\data`（容器挂载 `../data:/app/data`）。

### 12.2 日常运维

```powershell
cd D:\Knetsec_Ai\deploy
docker compose logs -f --tail 200 server   # 跟踪日志
docker compose restart server              # 重启
docker compose down                        # 停止（数据保留）
docker compose up -d --build               # 升级重建
docker compose exec server node -e "fetch('http://127.0.0.1:8787/health').then(r=>console.log(r.status))"
```

### 12.3 备份（容器方式）

```powershell
# 容器写共享卷，直接备份宿主机 data 目录即可；建议先停写
docker compose stop server
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
Copy-Item -Recurse -Force D:\Knetsec_Ai\data "D:\Backup\Knetsec_Ai-docker-$stamp"
docker compose start server
```

### 12.4 常见容器问题

| 现象 | 处理 |
|---|---|
| 构建上下文过大/很慢 | 确认 `deploy\Dockerfile.server.dockerignore` 生效，`node_modules` 未被打进上下文 |
| `server` 反复重启 | `docker compose logs server`；多为数据卷权限或 `.env` 值不合法 |
| `web` 502 | `server` 未健康；等健康检查通过或查看 server 日志 |
| 改端口不生效 | 修改 `deploy\.env` 的 `WEB_PORT` 后 `docker compose up -d` |
| 容器内时间不对 | 检查 `TZ` 变量（默认 Asia/Shanghai） |

### 12.5 容器资源与日志建议

| 项 | 建议 |
|---|---|
| CPU / 内存 | 2 核 / 2 GB 足够（采集是 I/O 等待型）；报告生成峰值 < 500 MB |
| 磁盘 | 给 `data` 卷预留 ≥ 5 GB，定期清理旧报告与备份 |
| 日志轮转 | 生产用 `docker compose logs` 或把 stdout 接到日志平台；避免无限增长 |
| 时区 | 固定 `TZ=Asia/Shanghai`，与调度器时区一致，报告区间口径才不会偏 |
| 健康检查 | compose 使用 `/health` 探活；不要用进程存在性代替 |

### 12.6 单机 vs 容器：怎么选

- **只想在自己电脑上长期跑**：用 Windows 本机 + `start.ps1`（最简单，数据在 `D:\Knetsec_Ai\data`）；
- **需要迁移机器/多人共用一台服务器**：用 Docker Compose（路径与依赖封装在镜像里，重建即可）；
- **需要公网访问**：两种方式都要在**前面加反向代理 + TLS**，不要直接暴露 8787；容器方式可直接复用 `deploy/nginx.conf` 的模式，把 nginx 换成带证书的实例。
