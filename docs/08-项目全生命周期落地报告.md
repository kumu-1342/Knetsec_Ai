## 2. 可行性结论

《01-可行性研究报告》的结论是**技术、合规、经济、运营四个维度均可行**，核心依据：

| 维度 | 关键依据 |
|---|---|
| 技术 | GitHub API / NVD API / CISA KEV / MSRC / arXiv 实测 200；Node 24 内置 SQLite 与 fetch，零原生编译 |
| 数据 | 主流源均有公开 API/RSS；CNVD 受本机网络限制，已设计代理与降级 |
| 合规 | 只聚合公开披露信息，只存摘要与链接，报告人工复核 |
| 经济 | 本机部署 0 云成本；可选 LLM 摘要约 5-15 元/月 |
| 运营 | 周报制作从 4-6 小时压缩到 30 分钟复核 |

实施后回看，这个判断成立：唯一持续的外部不确定性是上游限流与反爬（GitHub 60 次/小时、NVD 5 次/30 秒、Cisco RSS 反爬），已在架构上用「数据源即配置 + 失败隔离 + 运行记录可见」化解。

### 4.3 数据流（一次采集）

1. 调度器每 5 分钟扫描 sources：enabled=1 且 last_run_at + interval_minutes <= now；
2. 创建 fetch_runs（running），按 priority 串行执行；
3. 适配器把外部数据转成 RawItem（不写库、不去重）；
4. 归一化 → 生成 UID → 批内去重 → 跨源去重 → 富化；
5. 单事务批量入库（唯一键冲突计为重复）；
6. 回写源状态/计数、运行统计与结构化日志；critical/KEV 触发通知；
7. 周报定时任务（周一 08:00）与手动生成复用同一报告生成器。

### 5.2 UID 与三层去重

```text
uid = sha256(source_key + ':' + externalId)          // 有稳定外部 ID（GHSA/CVE/RSS guid）
uid = sha256(source_key + ':' + normalize(title))    // 无 ID 时退化为规范化标题哈希
跨源：CVE/GHSA 交集，或 3-gram Jaccard(标题) ≥ 0.85 且同分类且发布时间差 ≤ 3 天
```

去重的关键实现（apps/server/src/pipeline/dedupe.ts）：

```ts
/** 把字符串切成 3-gram 集合；长度不足 3 时退化为整串，避免短标题相似度恒为 0。 */
function buildGramSet(input: string): Set<string> {
  const text = input.replace(/\s+/g, ' ').trim();
  const grams = new Set<string>();
  if (text.length === 0) return grams;
  if (text.length <= GRAM_SIZE) { grams.add(text); return grams; }
  for (let i = 0; i <= text.length - GRAM_SIZE; i += 1) {
    grams.add(text.slice(i, i + GRAM_SIZE));
  }
  return grams;
}

/** Jaccard = |A ∩ B| / |A ∪ B|，取值 0-1；完全一致为 1，无公共 gram 为 0。 */
export function jaccardSimilarity(a: string, b: string): number {
  const setA = buildGramSet(titleFingerprint(a));
  const setB = buildGramSet(titleFingerprint(b));
  if (setA.size === 0 || setB.size === 0) return 0;
  const [small, large] = setA.size <= setB.size ? [setA, setB] : [setB, setA];
  let intersection = 0;
  for (const gram of small) if (large.has(gram)) intersection += 1;
  const union = setA.size + setB.size - intersection;
  return union === 0 ? 0 : intersection / union;
}
```

为什么用 3-gram 而不是编辑距离：中文标题没有空格，编辑距离对「同事件不同表述」过于严格；3-gram 集合对词序、标点、少量增删更鲁棒，且计算是线性的。阈值 0.85 经去重单测（27 条）验证，能拦住「同一 CVE 的媒体转述」，又不会误合并「同一厂商的同类漏洞公告」。

## 7. 报告生成实现

报告由两部分组成：

1. generator.ts：按分类与严重度把区间内情报组织成中文 Markdown，固定 9 章；
2. renderer.ts：把 Markdown 转成单文件 HTML（内联 CSS），可浏览器直接打印 PDF。

章节顺序：本周速览 → AI 安全 → 漏洞与补丁（表格）→ 网络安全 → 安全研究 → 工具与项目 → 政策与合规 → 本周数据统计 → 下期关注。排序规则：KEV 优先 → severity → importance → 时间倒序，每章最多 30 条。

```ts
/** 排序：KEV 优先，其次 severity 权重、importance、时间倒序。 */
export function compareReportItems(a: ItemDTO, b: ItemDTO): number {
  if (a.isKev !== b.isKev) return a.isKev ? -1 : 1;
  const severityDiff = SEVERITY_WEIGHT[b.severity] - SEVERITY_WEIGHT[a.severity];
  if (severityDiff !== 0) return severityDiff;
  if (b.importance !== a.importance) return b.importance - a.importance;
  return (b.publishedAt ?? b.fetchedAt).localeCompare(a.publishedAt ?? a.fetchedAt);
}
```

**安全要点**：渲染器先把所有外部文本做 HTML 转义，再生成标签；链接只允许 http(s) 与相对路径，杜绝 javascript: 伪协议。这是服务端「零渲染依赖」方案的核心收益——不必信任第三方库的默认转义。

产物落盘：

```text
data/reports/<id>-<type>-<yyyyMMdd>/report.md
data/reports/<id>-<type>-<yyyyMMdd>/report.html
```

### 8.2 统一请求层与鉴权

所有页面只通过 api/client.ts 访问后端，它负责：注入 Token、解信封、401 跳登录、错误提示、超时兜底。

```ts
// apps/web/src/api/client.ts（节选）
instance.interceptors.request.use((config) => {
  const token = localStorage.getItem(TOKEN_STORAGE_KEY);
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

instance.interceptors.response.use(
  (response) => response,
  (error: AxiosError<ApiFailure>) => {
    const status = error.response?.status ?? 0;
    const failure = error.response?.data;
    const message = failure && failure.success === false ? failure.error.message : fallbackMessage(error);
    if (status === 401) {
      const isLoginRequest = error.config?.url?.includes('/auth/login') ?? false;
      if (isLoginRequest) return Promise.reject(new ApiRequestError(message, 'UNAUTHORIZED', status));
      redirectToLogin();
      ElMessage.error('登录已过期，请重新登录');
    }
    return Promise.reject(new ApiRequestError(message, failure?.success === false ? failure.error.code : 'NETWORK_ERROR', status));
  },
);
```

## 9. 安全与合规设计

| 层 | 措施 |
|---|---|
| 密码 | scrypt(N=16384,r=8,p=1) + 16 字节随机盐 + timingSafeEqual，禁止明文/可逆存储 |
| 会话 | JWT HS256 12 小时；密钥自动生成并持久化 data/.jwt-secret（0600）；401 统一跳登录 |
| 权限 | admin 读写 / viewer 只读；写接口服务端强制校验，前端隐藏按钮只是体验优化 |
| 输入 | Zod 校验所有 query/body；排序字段白名单；SQL 全部参数化；LIKE 通配符转义 |
| 输出 | 报告 HTML 全量转义；链接协议白名单；面板 Markdown 经 DOMPurify |
| 传输/部署 | 默认仅监听 127.0.0.1；公网部署要求反向代理 + TLS；nginx 配置附 CSP/HSTS 等安全头 |
| 审计 | 登录、改密、增删源、触发采集、批量操作、生成/删除报告、改设置全部留痕 |
| 限流 | 登录 5 次/分/IP；bodyLimit 2MB |
| 合规 | 只聚合公开信息；只存标题/摘要/链接（摘要≤600 字）；不存全文；不提供利用代码；报告人工复核 |

### 10.3 实施中遇到的真实问题（含处理原因）

| # | 问题 | 原因 | 处理 | 结果 |
|---|---|---|---|---|
| 1 | 本机 Python 3.8.6 过旧 | 用户环境 | 改用 Node 24，不动用户 Python | 零环境变更 |
| 2 | npm install 首次耗时约 10 分钟 | 依赖树大 + registry 延迟 | 后台安装、期间并行写代码 | 424 包安装成功 |
| 3 | 根 TS 版本为 6.0.3（vue-tsc 解析到 6） | npm 提升 + 旧 tsconfig 用了废弃 baseUrl | 删 baseUrl、paths 改相对路径 | 前端 typecheck 通过 |
| 4 | @fastify/jwt 类型增强 TS2664 | 增强声明写错模块名 | 改为 declare module 'fastify' | 鉴权类型通过 |
| 5 | scrypt promisify 丢失 options 重载 | Node 类型定义多重重载 | 手写 Promise 包装 | 密码哈希正确 |
| 6 | vitest 全部无法启动 | 块注释里出现 */ 提前闭合 | 重写配置 | 134 用例可跑 |
| 7 | 报告 AI 章节混入普通漏洞 | 关键词 rag 命中 storage | 语义边界匹配 | 分类准确 |
| 8 | 会话中断（环境挂起）导致成员失败 | 外部因素 | 恢复成员上下文、按小步落盘继续 | 全部任务完成 |
| 9 | GitHub 配额耗尽导致 GHSA 403 | 未认证 60 次/小时 | 记录为外部约束，Token 可解；UI/日志可见 | 生产需配 Token |
| 10 | CNVD/CNNVD 不可达 | 本机 TLS 吊销检查离线 | 停用 + 代理开关 + 文档 | 不阻塞 |

这些问题的共同处理原则是：**不掩盖失败、不让单点阻塞全局、把配置项暴露给运维**。这正是「数据源即配置 + 失败隔离 + 运行记录可见」架构的价值。

## 13. 项目复盘

### 13.1 做对了什么

1. **契约先行**：先写 docs/00 + shared 类型，再并行开发，前后端联调几乎没有返工；
2. **数据源即配置**：39 个源全部是数据库记录，新增/停用不改代码；
3. **失败隔离**：单源失败只记录，采集任务照常完成（partial 状态），运营可在面板看到并重试；
4. **可观测**：运行记录含逐源日志，排障不需要翻服务器日志；
5. **零原生依赖**：node:sqlite + 内置 fetch，Windows 新机器装完就能跑。

### 13.2 不足与 v1.1 规划

| 优先级 | 事项 | 说明 |
|---|---|---|
| P1 | GitHub Token 引导 | 首次启动检测未配置 Token 时在面板提示，降低 403 概率 |
| P1 | 采集并发可配置 | 当前串行保守，可对稳定源开 2-3 并发缩短一轮时间 |
| P2 | ECharts 按需引入 | Dashboard chunk 约 1MB，按需引入可减半 |
| P2 | OpenAPI Schema 补全 | 自动生成前端客户端与更完整的 API 文档 |
| P2 | 报告模板可配置 | 章节顺序/条数/点评字段可视化配置 |
| P3 | 通知渠道扩展 | 邮件、Server 酱、Telegram |
| P3 | 多用户与 RBAC | 当前 admin/viewer 两角色，够单运营使用 |
| P3 | 迁移到 PostgreSQL | 数据量到百万级或多人协作时 |
