## 摘要

**结论：项目技术可行、合规可行、经济可行，建议立即立项落地。**

Knetsec_Ai 定位为「AI 安全 × 网络安全」实时情报平台：从 GitHub、国家漏洞库、厂商 PSIRT、研究机构与安全媒体等公开渠道自动采集情报，完成归一化、去重、分级与打标，自动生成结构化周报，并提供一套中文管理面板完成来源管理、任务调度、报告分发与运营。

本报告基于**本机真实环境勘察**（Node.js 24.22、npm 11.19、VS Code 1.146、Windows 11）与**真实网络探活**（GitHub API、NVD API、微软 MSRC、arXiv、CISA KEV 均返回 200；CNVD 与 OSV 在当前网络下不可达）给出可行性判断，并逐项拆解了需要做的细节、实施中会遇到的真实问题及其处理原因。

核心判断：

| 维度 | 判断 | 依据 |
|---|---|---|
| 技术可行性 | ✅ 高 | 主流数据源均有公开 API/RSS；Node 24 内置 SQLite 与 fetch，零原生编译即可落地 |
| 数据可行性 | ✅ 中高 | 5 类核心源实测可达；CNVD 需代理，已设计降级与代理开关 |
| 合规可行性 | ✅ 可行 | 只聚合公开披露信息，只存标题/摘要/链接，不碰未授权测试与武器化代码 |
| 经济可行性 | ✅ 可行 | 本机部署零云成本；可选 LLM 摘要按量计费，月成本可控制在 10 元内 |
| 运营可行性 | ✅ 高 | 把每周 4-6 小时的人工巡检压缩到 30 分钟复核 |
| 维护成本 | ⚠️ 中 | 上游页面/字段会变，需保留适配器热插拔与失败可见能力 |

## 1. 项目背景

### 1.1 业务场景

运营方正在建设「AI × 网络安全」知识星球，固定栏目包含：

- ① AI 安全情报周报（每周一）
- ② 深度拆解（提示注入、Agent 越权、RAG 数据泄露……）
- ⑤ 案例复盘 / 问答精选

其中周报与案例复盘高度依赖**持续、及时、可检索**的情报输入。当前人工方式存在四个结构性痛点：

1. **入口分散**：GitHub Advisory、NVD、CNVD/CNNVD、微软 MSRC、Cisco/Fortinet PSIRT、Google Project Zero、Unit 42、AWS/Cloudflare 安全博客、arXiv、OpenAI/Anthropic 官方博客、Hugging Face、The Hacker News……每天几十个入口；
2. **重复严重**：同一个 CVE 会被 NVD、GHSA、厂商公告、安全媒体重复报道 3-8 次，人工去重耗时且容易遗漏；
3. **时效窗口短**：CISA KEV（已知被利用漏洞）与 0day 的窗口只有数小时，人工巡检必然滞后；
4. **无法沉淀**：收集结果散落在浏览器收藏夹/微信收藏，无法检索、无法统计、无法复用为报告与课程素材。

### 1.2 项目目标

用一套工具打通「**巡检 → 汇总 → 去重 → 分级 → 打标 → 成稿 → 分发**」全链路，让人只做两件事：**判断**（这条情报值不值得写）与**点评**（一句话观点）。

可量化的目标：

- 单次全量巡检从人工 40-60 分钟 → 自动 2-5 分钟完成；
- 周报成稿从人工 4-6 小时 → 30 分钟复核 + 微调；
- 情报入库 100% 带来源、时间、分类、严重度、标签；
- 支持至少 20 个内置数据源、5 类来源，失败源在面板可见且可单独重试；
- 覆盖「AI 安全」与「网络安全」双主线，AI 安全单独成章。

### 2.3 合规前置

- 只采集公开披露信息，不绕过登录、付费墙、反爬策略；
- 只存标题、摘要（≤600 字）、原文链接，**不全文转载**，报告注明来源；
- 不提供漏洞利用代码，PoC 只保留链接；
- 报告发布前由运营人工复核，工具只提供初稿；
- 管理面板默认仅监听 127.0.0.1，公网部署需加反向代理与 TLS；
- 遵守《网络安全法》《数据安全法》《个人信息保护法》《生成式人工智能服务管理暂行办法》相关要求。

## 4. 技术可行性论证

### 4.1 技术栈选择

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Node 24 + TypeScript + Fastify + node:sqlite**（选用） | 与前端同语言共享类型；内置 SQLite/fetch 零原生编译；本机已具备 | 生态在安全数据解析上略弱于 Python | ✅ 选用 |
| Python 3.11 + FastAPI | 爬虫/解析生态成熟 | 本机 Python 3.8 过旧，需升级或装多版本；交付给非全栈用户维护成本高 | ❌ 弃用 |
| Java/Go 单体 | 性能与工程化强 | 开发效率低，与前端类型割裂，本机无现成环境 | ❌ 弃用 |
| 云托管 SaaS（聚合 API） | 免运维 | 付费、数据出境、定制受限 | 作为备选，不作为主线 |

**为什么 SQLite 而不是 PostgreSQL/MySQL**：单机部署、单运营者、日增千级数据量，SQLite（WAL 模式）完全够用；零安装、单文件备份、迁移简单。数据量增长到百万级或多人协作时再平滑迁移（SQL 层已收敛在 repo 中）。

**为什么不用消息队列/Redis**：单机任务量小，采集与报告用进程内调度 + 单运行锁即可；引入 MQ/Redis 只会增加部署复杂度。

### 4.2 关键技术点与验证

| 技术点 | 验证方式 | 结论 |
|---|---|---|
| GitHub API 分页与限流 | 实测 200，响应 <1s | 可行；Token 配置后额度充足 |
| NVD 2.0 API 日期窗口 | 实测 200，9s | 可行；需控制频率 5 次/30 秒 |
| RSS/Atom 解析（含命名空间） | fast-xml-parser 方案成熟 | 可行；需处理 CDATA 与 HTML 摘要清洗 |
| 跨源去重 | 3-gram Jaccard + CVE/GHSA 交集 | 可行；阈值 0.85，误杀率可控 |
| 中文标签与分级 | 规则词典 + CVSS/KEV 推导 | 可行；LLM 仅作可选增强 |
| SQLite 并发 | WAL + busy_timeout=5s + 批量事务 | 可行；单写者模型足够 |
| 管理面板 SSE/轮询 | 运行日志轮询（2s） | 可行；实现简单、稳定 |

### 4.3 性能与容量估算

- 日新增情报：20 源 × 平均 10-30 条 ≈ 200-600 条/日，年增 7-22 万条；
- 单表 20 万行 + 4 个索引，SQLite 查询毫秒级；
- 单次全量采集：串行 2-6 分钟（受 NVD 限流影响），可配置并发；
- 内存占用：服务端常驻约 80-150MB；前端构建产物约 1.5-2.5MB gzip 后 <1MB。

## 6. 实施细节与关键决策记录

### 6.1 数据模型

六张核心表：`sources`（数据源）、`items`（情报）、`fetch_runs`（运行记录）、`reports`（报告）、`settings`（设置）、`users`/`audit_logs`（账号与审计）。完整字段见《03-总体架构设计》。

去重键设计：

```text
uid = sha256(source_key + ':' + externalId)      // 有稳定外部 ID 时（GHSA/CVE/RSS guid）
uid = sha256(source_key + ':' + normalize(title)) // 否则退化为标题哈希
跨源：CVE/GHSA 交集 或 3-gram Jaccard(标题) ≥ 0.85 且同分类且发布时间差 ≤ 3 天
```

### 6.2 采集流水线

```text
调度器(每5分钟) → 到期源入队 → 创建 run → 逐源 fetch
  → normalize（补默认值/时间/语言/UID/ID 提取）
  → dedupe（批内 + 库内 + 跨源）
  → enrich（severity/标签/importance/可选 LLM）
  → 批量入库（ON CONFLICT DO NOTHING）
  → 更新源状态、运行统计、审计
  → critical/KEV 触发通知
```

### 6.3 真实问题与处理（"处理遇到的原因"）

| 问题 | 根因 | 处理方案 | 结果 |
|---|---|---|---|
| CNVD 无法访问 | 本机 schannel 吊销检查离线（CRYPT_E_REVOCATION_OFFLINE），非站点封禁 | 源保留、默认停用；增加 `KNETSEC_HTTP_PROXY`；失败不影响其他源；文档给出代理与替代方案（CNNVD、厂商中文公告） | 不阻塞主线 |
| OSV API 超时 | 网络路由/出口限制 | 不纳入首版，作为可选扩展 | — |
| BleepingComputer 403 | 站点反爬（UA/Cloudflare） | 换用可达媒体源；登记但停用 | — |
| NVD 网页 403 | 官方限制非浏览器访问 | 只走官方 API，不爬网页 | 合规且稳定 |
| GitHub 未认证限流 60/h | 免费额度 | 支持 GITHUB_TOKEN；单轮控制请求数；429 指数退避 | 可稳定运行 |
| NVD 5 次/30 秒 | 官方限流 | 请求间隔 6s；配置 Key 后 0.6s；单轮仅拉 7 天 | 单轮约 1-2 分钟 |
| Python 3.8 过旧 | 用户环境 | 改用 Node 24，避免改动用户系统 | 零环境变更 |
| 报告需同时给 Markdown 与可直接打印的版本 | 知识星球/公众号排版 | Markdown + 单文件 HTML 双输出 | 复制即用 |
| 面板要能验证「源还能不能用」 | 上游经常改版 | 「试采」接口：不写库、返回样本标题与耗时 | 运营自助排障 |
| 前端展示一致性与重复定义类型 | 多人协作 | 前后端共享 `@knetsec/shared` 类型包，契约先行 | 减少联调摩擦 |

### 6.4 安全设计

- 密码：scrypt（N=16384）+ 随机盐 + timingSafeEqual；
- 会话：JWT HS256，12 小时过期，密钥自动生成并持久化到 `data/.jwt-secret`（0600）；
- 接口：登录限流 5 次/分/IP、2MB 请求体上限、Zod 参数校验、SQL 全参数化；
- 前端：报告 Markdown 经 DOMPurify 消毒，防 XSS；
- 审计：登录、改密、增删改源、触发采集、生成/删除报告、改设置全部留痕；
- 网络：默认仅监听 127.0.0.1；公网部署必须反代 + TLS + 修改默认密码。

## 10. 结论与建议

**可行性结论：可行，建议落地。**

理由：

1. 核心数据源（GitHub、NVD、CISA、MSRC、arXiv）实测可达，覆盖「AI 安全 + 网络安全」双主线所需的大部分信息；
2. Node 24 内置能力让系统零原生依赖、单命令启动，交付与维护成本低；
3. 架构把「数据源」抽象为数据而非代码，能长期对抗上游变化；
4. 成本近乎为零，收益（时间、内容资产、时效）明确；
5. 合规边界清晰：只聚合公开披露信息、只存摘要与链接、报告人工复核。

**建议**：

- 第一期先落本机版（本文方案），跑通 2-4 周再考虑公网部署；
- 尽快申请 GitHub Token 与 NVD API Key（免费，显著提升稳定性）；
- CNVD 待网络条件允许时通过代理启用，不要为了单一源阻塞整体上线；
- 周报先「机器初稿 + 人工点评」，稳定后再考虑 LLM 自动点评；
- 数据每日备份（拷贝 `data` 目录即可）。
