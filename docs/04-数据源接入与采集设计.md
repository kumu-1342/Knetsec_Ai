# 04 · 数据源接入与采集设计

> 本文是 Knetsec_Ai 采集子系统的设计说明与运维手册，与 docs/00-项目总览与架构契约.md 第 7、8 节一一对应。
> 读者：接手维护采集器的后端开发、需要新增数据源的运营、排障的运维。
> 版本：v1.0（2026-11-17）。所有"实测"结论均在本机（Windows 10 + Node 24 + 直连网络）用与线上同一套 HttpClient 验证得到。

## 1. 采集链路总览

采集子系统负责回答一个问题：**"外面发生了什么"**。它把分散在 GitHub、NVD、CISA、微软、arXiv、厂商博客、安全媒体的公开信息，变成统一结构、可直接入库与生成报告的情报条目。

完整链路（一次采集）：

```text
调度器（每 5 分钟扫描 sources 表）
   │  选出 enabled=1 且 last_run_at + interval_minutes <= now 的源
   ▼
pipeline/orchestrator.ts（backend 实现）
   │  创建 fetch_runs 记录（status=running），按 priority 排序逐源执行
   ▼
collectors/index.ts → createCollector(source) → 具体适配器
   │  适配器只做一件事：HTTP 请求 + 字段映射 → RawItem[]
   ▼
pipeline/normalize.ts（collector 实现）
   │  补默认值 / 清洗摘要 / 合并 CVE-GHSA / 生成 uid / 语言判定
   ▼
pipeline/dedupe.ts（collector 实现）
   │  批内去重（uid、编号、标题相似度）→ 库内跨源判定（±3 天窗口）
   ▼
pipeline/enrich.ts（backend 实现）
   │  CVSS/KEV → severity、AI 安全标签、importance、可选 LLM 摘要
   ▼
items 表（INSERT ... ON CONFLICT(uid) DO NOTHING）
```

设计上刻意把链路切成两段责任：

| 阶段 | 归属 | 允许做的事 | 禁止做的事 |
|---|---|---|---|
| collectors/** | collector-core | 发 HTTP、解析 JSON/XML/HTML、字段映射、返回 RawItem | 写数据库、去重、最终分类 |
| pipeline/normalize.ts、dedupe.ts | collector-core | 补默认值、生成 uid、清洗、去重 | 发请求、写库 |
| pipeline/enrich.ts、orchestrator.ts | backend-core | 打标、分级、落库、更新源状态 | 绕过适配器直接抓取 |

这样切分带来三个实际好处：

1. **适配器可以被单测**：给它一个假的 CollectorContext（假 http、固定 now），断言输出条目，不需要数据库；
2. **新增数据源不改流水线**：90% 的新源只是"另一个 RSS/JSON/HTML 列表"，改配置即可；
3. **去重规则只有一份**：如果每个适配器自己判重，很快会出现"GitHub 源认为重复、NVD 源认为不重复"的混乱。

## 2. 适配器契约

接口定义在 packages/shared/src/collector.ts（零依赖，前后端与测试共用）：

```ts
export interface CollectorAdapter {
  readonly id: AdapterId;
  fetch(ctx: CollectorContext): Promise<CollectorResult>;
}

export interface CollectorContext {
  source: SourceDescriptor;   // 来自 sources 表的运行期描述（key/name/category/config/...）
  now: Date;                  // 采集基准时间（测试注入固定值以保证幂等）
  logger: CollectorLogger;    // 结构化日志（pino 或测试桩）
  http: CollectorHttpClient;  // 带超时/重试/UA/代理的 HTTP 客户端
  settings: AppSettings;      // 运行期设置（AI 关键词、关注词等）
  secrets: { githubToken: string; nvdApiKey: string };
}

export interface CollectorResult {
  items: RawItem[];
  cursor?: string;            // 预留增量游标
  warnings?: string[];        // 非致命告警，写入运行日志
}

export interface RawItem {
  externalId?: string;        // 上游稳定 ID（GHSA 号/CVE 号/RSS guid）
  title: string;              // 必填
  summary?: string;
  url?: string;
  author?: string;
  publishedAt?: string;       // ISO 8601，缺失时流水线回退 fetchedAt
  category?: ItemCategory;    // 建议值，流水线可校正
  tags?: string[];
  severity?: Severity;
  cveIds?: string[];
  ghsaIds?: string[];
  cvssScore?: number;
  isKev?: boolean;
  vendor?: string;
  lang?: 'zh' | 'en' | 'other';
  raw?: unknown;              // 原始快照，落库前裁剪到 16KB
}
```

六条硬约束（违反任何一条都会在联调阶段暴露）：

1. **只做转换**：不写库、不去重、不调用其他适配器；
2. **必填只有 title**：其余字段尽力提供，缺失由归一化层兜底，绝不因缺字段抛错；
3. **幂等**：同一份上游数据重复采集必须产生相同 externalId（uid 才能稳定）；
4. **时效**：默认只返回最近 30 天内容（各源可配置），避免首次接入灌入历史数据；
5. **容错**：单条解析失败 → 跳过 + warnings.push；整体失败才抛错（由编排器记为源失败）；
6. **限流**：所有请求走 ctx.http，适配器内部串行 + sleep，禁止并发打上游。

### 2.1 配置校验

所有适配器都用 zod 校验 config，且**每个字段都带默认值兜底**（.catch 或 .default）。原因：config 存在数据库里，管理员可以在面板手改 JSON，一个拼错的数字不应该让源永久失效。

```ts
const ConfigSchema = z.object({
  perPage: z.number().int().min(1).max(100).catch(50),
  severities: z.array(z.string()).catch(['critical', 'high']),
  days: z.number().int().min(1).max(365).catch(30),
});
const config = ConfigSchema.safeParse(source.config ?? {}).success
  ? ConfigSchema.parse(source.config)
  : ConfigSchema.parse({});
```

### 2.2 请求节奏

| 上游 | 限制 | 适配器策略 |
|---|---|---|
| GitHub 普通接口 | 未认证 60 次/小时 | 每源请求数 ≤ 3，请求间 300ms；有 token 时限额 5000/小时 |
| GitHub 搜索接口 | 未认证 10 次/分钟 | 单次只发 1 个请求，不翻页 |
| NVD | 未认证 5 次/30 秒 | 请求间 6000ms；有 API Key 时 50 次/30 秒 → 600ms |
| arXiv | 官方建议 3 秒/次 | 单请求；被限流时识别 "Rate exceeded." 并重试一次 |
| 其他（RSS/厂商/媒体） | 无明确公开限制 | 请求间 300ms，串行 |

这些间隔直接决定了一轮采集的耗时：nvd-ai 有 5 个关键词（5 次请求 × 6 秒）约 30 秒，是整个流水线里最慢的源，因此它的采集间隔设为 12 小时而不是 6 小时。

## 3. 十个适配器详解

### 3.1 github_advisories —— GitHub 安全公告库

- **接口**：GET https://api.github.com/advisories
- **请求头**：accept: application/vnd.github+json、x-github-api-version: 2022-11-28、有 GITHUB_TOKEN 时附带 authorization: Bearer [token]
- **参数**：per_page、severity、published（ISO 时间）、sort=published、direction=desc
- **字段映射**：ghsa_id → externalId；summary → title；description → summary（清洗截断 600）；html_url → url；published_at → publishedAt；vulnerabilities[].package.name/ecosystem → 标签；cvss.score → cvssScore；cve_id → cveIds

**实测坑（很重要）**：severity 参数只接受**单个**值，传 "critical,high" 会返回 HTTP 422：

```json
{"message":"Invalid request. Invalid input: critical,high is not a possible value. Must be one of the following: unknown, low, medium, high, critical."}
```

因此适配器对每个 severity 各发一次请求（默认 critical + high 共 2 次），本地按 ghsa_id 去重。这是"未认证额度 60 次/小时"下仍然安全的原因：单源单次最多 2 次请求。

**两种请求模式（实测强制）**：

| 配置 | 请求方式 | 原因 |
|---|---|---|
| 未配置 ecosystems | 按 severity 逐个请求（每次 1 个 severity + published 窗口） | 接口只接受单值 severity；published 必须 date-only |
| 配置了 ecosystems | 按 ecosystem 逐个请求（不带 severity/published），本地过滤 severities 与 days | ① 只有 ecosystem 参数能拿回 vulnerabilities[].package（AI 生态判定依赖包名）；② 实测 ecosystem + published 同时使用返回 0 条（上游过滤语义不一致） |

因此「AI 生态专项源」的请求量 = ecosystems 数量（上限 3），而不是 severity 数量；单源单轮仍控制在 2-3 次请求内。

**分类建议**：命中 AI 生态组件（pytorch / langchain / ollama / vllm / transformers / mcp 等关键词，见 collectors/helpers.ts 的 AI_STACK_KEYWORDS）→ category=ai-security，否则 vuln。这只是建议值，enrich 会结合 settings.aiSecurityKeywords 再校正。

**关键词匹配必须带语义边界**（实测踩坑）：关键词表里有 cuda / ray / torch / mcp 这类短词，用 includes 子串匹配会把 "Barracuda"（cuda）、"Arraytics"（ray）、"McPherson"（mcp）误判为 AI 组件，导致 CISA KEV 的 Barracuda 漏洞被错误归到 ai-security。当前实现（helpers.ts 的 matchAiKeyword）要求关键词前后必须是非 ASCII 字母数字字符或字符串首尾：中文关键词（大模型）同样能命中，而 "CUDA-enabled"、"cuda:" 这类写法仍然命中。

配置示例：

```json
{ "perPage": 50, "severities": ["critical", "high"], "days": 30, "ecosystems": ["pip", "npm"] }
```

### 3.2 github_search —— GitHub 仓库搜索

- **接口**：GET https://api.github.com/search/repositories?q=...&sort=updated&order=desc&per_page=...
- **externalId**：full_name + "@" + updated_at。带上更新时间是刻意的：这样仓库有新提交时会作为新条目出现，而不是被 uid 去重永久吞掉。
- **字段**：full_name → title；description + 星标数 → summary；html_url → url；topics/language → tags；category=tool
- **限流**：搜索接口未认证 10 次/分钟，适配器单次只发 1 个请求、不翻页。

### 3.3 github_releases —— 重点 AI 项目发布

- **接口**：GET https://api.github.com/repos/{owner}/{repo}/releases?per_page=N（每仓库 1 次请求）
- **externalId**：仓库名 + "@" + tag_name，同一版本重复采集 uid 稳定
- **标题**：repo + " " + tag_name（例如 "vllm-project/vllm v0.6.3"），报告里一眼能看出项目与版本
- **summary**：release body 清洗为纯文本、截断 600；跳过 draft，prerelease 打标签
- **默认监控项目**：vllm-project/vllm、langchain-ai/langchain、ollama/ollama、promptfoo/promptfoo、BerriAI/litellm（可在 config.repos 覆盖，非法 repo 名会被跳过并记 warning）

### 3.4 nvd_cve —— NVD 漏洞库

- **接口**：GET https://services.nvd.nist.gov/rest/json/cves/2.0?pubStartDate&pubEndDate&resultsPerPage&keywordSearch
- **时间窗**：1-120 天（NVD 硬上限 120），默认 7 天；时间格式不带时区（yyyy-MM-ddTHH:mm:ss.SSS），带 Z 在部分网关会被拒
- **限流**：请求间隔 6000ms，有 NVD_API_KEY 时 600ms；关键词搜索每个关键词一次请求，最多 5 个
- **字段映射**：cve.id → externalId + cveIds；descriptions(lang=en) → summary；metrics.cvssMetricV40|V31|V30|V2 的 cvssData.baseScore/baseSeverity → cvssScore/severity（优先 Primary 来源）；published → publishedAt；url 拼 https://nvd.nist.gov/vuln/detail/{id}
- **过滤**：config.minCvss 可只保留高分漏洞（nvd-recent 用 minCvss=7 控制噪音）

**降级策略**：单个关键词请求失败只记 warning 并继续下一个；全部请求失败才抛错。这样"5 个关键词里挂 1 个"不会让整个源失败。

### 3.5 cisa_kev —— CISA 已知被利用漏洞

- **接口**：GET https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json
- **特点**：整份清单约 1.8MB、上千条，单次全量下载后本地按 dateAdded 过滤最近 N 天，只发 1 次请求
- **字段映射**：cveID → externalId + cveIds；vulnerabilityName → title（前缀 CVE 号）；shortDescription + requiredAction + dueDate → summary；dateAdded → publishedAt；vendorProject → vendor；url 指向 NVD 详情
- **严重度**：KEV 不提供 CVSS，但"在野利用"本身就是最高风险信号 → severity=high；若 knownRansomwareCampaignUse=Known 则升为 critical
- **标记**：isKev=true、tags 固定包含 kev/cisa/in-the-wild，勒索软件条目加 ransomware

### 3.6 msrc_cvrf —— 微软 MSRC 安全公告

- **接口**：GET https://api.msrc.microsoft.com/cvrf/v3.0/updates
- **返回**：公告索引 JSON（实测 217 条），字段 ID / Alias / DocumentTitle / Severity / InitialReleaseDate / CurrentReleaseDate / CvrfUrl
- **为什么只解析索引不解析 CVRF XML**：单个 CVRF 文档是复杂 XML（产品树 + 漏洞树 + CVSS 组合），解析成本高、极易随上游改版而崩；索引层已能回答"本月有哪些公告、何时发布"，CVE 明细由 NVD 源补齐。若确需全文，把 config.fetchDocument 设为 true（预留开关）。
- **字段映射**：ID → externalId；"ID + DocumentTitle" → title；严重度/发布日期拼成 summary；CurrentReleaseDate ?? InitialReleaseDate → publishedAt；vendor 固定 Microsoft

### 3.7 arxiv —— arXiv 预印本

- **接口**：GET https://export.arxiv.org/api/query?search_query=...&sortBy=submittedDate&sortOrder=descending&max_results=N
- **query 构造**：分类用 cat:cs.CR，多个分类用 +OR+ 连接；有关键词时拼成 (cat:...)+AND+(all:"keyword"+OR+...)。注意不能用 URLSearchParams，它会把结构性加号编码成 %2B 破坏语法，因此对每个词元单独 encodeURIComponent。
- **解析**：fast-xml-parser 解析 Atom；externalId 取 id 并**去掉版本号后缀**（2410.12345v2 → 2410.12345），否则论文每次更新都会变成新条目；url 取 rel=alternate 链接；作者取前 3 位；tags 取 category term；category=research
- **限流坑**：arXiv 超限时返回 **HTTP 200 + 纯文本 "Rate exceeded."**（假成功），适配器识别后 sleep 3 秒重试一次，仍失败则抛 UPSTREAM_ERROR 并提示降低频率

### 3.8 rss —— 通用 RSS 2.0 / Atom / RDF

- **支持三种格式**：RSS 2.0（rss.channel.item）、Atom（feed.entry）、RSS 1.0 / RDF（rdf:RDF.item）
- **字段兼容**：title/link/guid/pubDate/description/content:encoded/author/dc:creator；CDATA 由 fast-xml-parser 自动合并进文本；带属性的节点（guid isPermaLink=false）用 textOf 统一取文本
- **清洗**：description/content 里的 HTML → 纯文本，截断 600
- **时间**：兼容 RFC822 与 ISO；无法解析时省略该字段（归一化层回退 fetchedAt）
- **过滤**：keepDays（默认 30）按发布时间过滤，maxItems 截断；按时间倒序后取前 N 条
- **链接**：相对链接用 new URL 解析为绝对地址

一个适配器覆盖 20+ 个媒体/厂商/研究源，这是"新增源不改代码"的核心。

### 3.9 json_list —— 通用 JSON 列表

- **配置**：url、itemsPath（点路径，支持数组下标）、fieldMap（title/url/publishedAt/summary/author/externalId 的点路径）、headers、maxItems、keepDays、category
- **取值**：getByPath 容错解析（路径不存在返回 undefined，不抛错）；itemsPath 配错时返回 warning "itemsPath 未取到条目数组"，这是最常见的接入错误
- **相对链接**：用 new URL 基于请求地址解析

配置示例（FIRST EPSS 评分接口，已在 seed 中作为示例登记）：

```json
{
  "url": "https://api.first.org/data/v1/epss?order=!epss&limit=50",
  "itemsPath": "data",
  "fieldMap": { "title": "cve", "url": "cve", "publishedAt": "date", "summary": "epss", "externalId": "cve" },
  "maxItems": 30,
  "keepDays": 7,
  "category": "vuln"
}
```

### 3.10 html_list —— 通用 HTML 列表页

- **配置**：url、itemSelector、titleSelector、linkSelector、dateSelector?、category、maxItems、keepDays
- **解析**：cheerio 选择器；标题取 titleSelector 文本，为空时退回条目自身文本；链接取 href 并用 new URL 解析为绝对地址；日期优先 dateSelector，缺失时用正则从条目文本兜底提取 yyyy-MM-dd / yyyy年MM月dd日
- **失效检测**：itemSelector 匹配 0 条 → 抛 UPSTREAM_ERROR（提示"站点结构可能变更或返回了验证页"），而不是静默返回空结果——这样面板的 last_error 能让运维立刻看到问题
- **合规**：只抓公开列表页的"标题 + 链接 + 日期"，不登录、不绕反爬、不抓正文

当前用于 CNVD / CNNVD（两者实测不可达，默认停用，见第 5 节）。

## 4. 归一化与去重规则

### 4.1 归一化（pipeline/normalize.ts）

| 字段 | 规则 | 为什么 |
|---|---|---|
| uid | 有 externalId：sha256(sourceKey + ":" + externalId)；无：sha256(sourceKey + ":" + 规范化标题) | 幂等的根基：同一内容重复采集 uid 不变 |
| 标题规范化 | NFKC（全角→半角）→ 小写 → 非字母数字折叠为连字符 → 去首尾连字符 | 上游标题的标点/大小写差异不应产生重复条目 |
| title | 清洗 HTML、折叠空白、截断 500 字；空标题回退"（无标题）" | items.title NOT NULL，不能因为脏数据炸库 |
| summary | 去标签/脚本/多余空白，截断 600 字（超出加省略号） | 面板与报告只需要纯文本摘要 |
| publishedAt | 解析 ISO/RFC822/纯日期；无法解析或超前 1 天以上 → 回退 fetchedAt | 上游时钟异常不能污染列表排序 |
| category | 适配器建议值合法则用，否则按源类别映射（github→tool、vuln-db→vuln、vendor→vuln、research→research、media→news、community→news） | 保证枚举合法，前端不会渲染出未定义分类 |
| severity | 合法值直接用，否则 unknown | 同上 |
| cvssScore | 只接受 0-10 有限数字，保留 1 位小数 | 防止脏数据把图表尺度撑爆 |
| cveIds/ghsaIds | 适配器给出的 + 从标题/摘要正则提取（CVE-年份-序号、GHSA-xxxx-xxxx-xxxx），合并去重大写排序 | 编号是跨源关联最可靠的依据 |
| tags | 去空、去重（大小写不敏感）、最多 16 个 | 防止标签爆炸 |
| lang | 命中 CJK → zh；有拉丁字母 → en；否则 other | 报告按语言分组、前端展示 |
| importance | 固定 0 | 该值依赖运营设置（关注关键词），属 enrich 职责 |
| raw | JSON 序列化；超过 16KB 时改存 {truncated:true, bytes, sample} | 截断字符串会破坏 JSON 结构，排障页 JSON.parse 会崩 |

### 4.2 去重（pipeline/dedupe.ts）

三层判定，命中任意一层即视为重复：

1. **uid 相同**：同一源重复采集，直接合并；
2. **CVE / GHSA 交集**：不同源报道同一漏洞，编号是最可靠的关联依据（不限制 category，因为同一漏洞可能被归到 ai-security 或 vuln）；
3. **标题相似度 ≥ 0.85 且 category 相同**：覆盖"媒体转述同一事件、编号缺失"的情况。

标题相似度用 3-gram Jaccard：

- titleFingerprint：小写 → 去标点 → 去停用词（英文虚词 + 中文虚词）→ 单空格连接；函数幂等；
- 3-gram 集合（字符级），Jaccard = |A∩B| / |A∪B|；
- 中文不引分词词典：整串保留后仍能用字符 3-gram 表达相似度，代价是中文标题只有标点/空白处能切出词元。

**阈值 0.85 的实测含义**（这是运维最常问的问题）：

| 标题对 | 相似度 | 判定 |
|---|---|---|
| "Critical OpenSSL vulnerability allows remote code execution" vs 仅大小写/停用词不同的同一句 | 1.00 | 判重 |
| "Microsoft patches critical Windows RCE vulnerability..." vs "...RCE vulnerabilities..." | 0.91 | 判重（屈折变化） |
| "Critical OpenSSL vulnerability allows..." vs "...permits..." | 0.77 | 不判重（换动词差异已超阈值） |
| "Critical RCE in OpenSSL" vs "Windows kernel privilege escalation" | 约 0.05 | 不判重 |

结论：0.85 是**保守**取值——只有标题几乎一致才合并。刻意如此：漏合并可由运营手工处理（面板批量操作），错合并会永久丢失独立情报。

批内去重的保留策略：命中重复时比较信息完整度（摘要长度、tags 数、是否有 url/CVSS/KEV/编号），保留更全的一条，但**位置保持首次出现的位置**，不打乱适配器的时间顺序。

跨源判定（findCrossSourceDuplicate）：

```sql
SELECT id, uid, title, cve_ids, ghsa_ids, published_at
FROM items
WHERE category = ? AND published_at IS NOT NULL
  AND published_at >= ? AND published_at <= ?   -- 发布时间 ±3 天
  AND uid <> ?                                  -- 排除自身（重复采集不是跨源重复）
ORDER BY published_at DESC
LIMIT ?                                         -- 200，防止全表扫描
```

- 时间窗 ±3 天：防止把周期性同标题公告（每周例行发布）误判为同一事件；
- category 隔离：安全论文与新闻稿标题可能高度相似，但业务分类不同，不应互相吞掉；
- 全部参数化 + LIMIT，杜绝注入与拖库；
- 查不到表（首次启动前调用）或 SQL 异常时安全降级为"不重复"，不影响采集。

合计成功 12/13（unit42 计入环境类），已远超"至少 5 个源成功"的验收要求。

- **失败分类（这是本节最重要的运维结论）**：LIVE 测试把失败分两类，避免"网络抽奖"掩盖真实回归：
  - **环境类**：网络不可达、未认证配额耗尽（GitHub 60 次/小时用尽后返回 403 rate limit）、站点反爬 403 → 记为 NETWORK 并打印警告，**不判失败**；
  - **代码类**：解析异常、字段缺失、结构变更、空结果且无环境类告警 → **判失败**（这才是适配器回归信号）。
- 实测中定位并修掉的 3 个真实缺陷（都已回归到代码/文档）：
  1. **GHSA published 参数格式**：传带毫秒的完整 ISO 会被 GitHub 判为非法日期并返回 422，必须用 date-only（YYYY-MM-DD）；
  2. **GHSA ecosystem 与 published 不能同时用**：两者一起传会返回 0 条（上游过滤语义不一致），因此适配器在配置 ecosystems 时改用"按 ecosystem 请求 + 本地按 days 过滤"，并因此能拿回 vulnerabilities[].package 数据；
  3. **AI 关键词子串误判**：matchAiKeyword 早期用 includes，导致 "Barracuda" 命中 cuda、"Arraytics" 命中 ray、"McPherson" 命中 mcp，把普通漏洞误分类到 ai-security；已改为语义边界匹配（关键词前后必须是非 ASCII 字母数字），并补了回归单测。
- 其余不可达源的原因（不需修代码）：
  1. **网络层不可达**（project-zero / anthropic / hf-blog / thehackernews）：DNS 或 TCP 连不上，需代理；
  2. **反爬拒绝**（securityweek / bleepingcomputer 403、cnvd 521、cnnvd 验证页）：需要代理 + 浏览器 UA，属于我方刻意不绕过反爬的边界；
  3. **上游下线**（fortinet 404、anthropic feed 路径不存在）：源本身没有订阅地址了，保留登记等官方恢复。
- **配额提醒**：GitHub 未认证额度 60 次/小时，一轮 LIVE（GHSA 2 + GHSA-AI 2 + releases 5 + search 2 = 11 次）跑 5 轮就会耗尽；连续实测前先配置 GITHUB_TOKEN（额度 5000 次/小时），否则 GitHub 相关源会显示 NETWORK 状态。

## 6. 新增数据源步骤

### 6.1 情形 A：已有适配器能覆盖（最常见，零代码）

1. 确认目标地址：RSS/Atom 用 rss 适配器；JSON 接口用 json_list；HTML 列表用 html_list；

3. 面板「数据源」→「新增」也可以直接建（适用于临时验证，seed 会在下次启动时幂等补齐）；
4. 点「试采」，看返回样本标题是否正常；不正常就调 itemsPath / 选择器；
5. 更新 docs/04 §5 的清单表。

示例（新增一个安全媒体 RSS）：

  "key": "example-media",
  "name": "示例安全媒体",
  "category": "media",
  "adapter": "rss",
  "url": "https://example.com/",
  "config": { "url": "https://example.com/feed/", "maxItems": 20, "keepDays": 30, "category": "cyber" },

  "intervalMinutes": 360,

### 6.2 情形 B：已有适配器但需要配置技巧

- NVD 关键词源：keywords 最多 5 个（每个关键词一次请求，未认证 6 秒/次），days ≤ 120；
- GHSA 生态过滤：ecosystems 填 pip/npm/maven/go/rubygems 等；severities 最多 3 个（每个一次请求）；
- GitHub 搜索：query 用 GitHub 搜索语法，perPage ≤ 50，单源单次只发 1 个请求，别建太多搜索源（未认证 10 次/分钟共享额度）；
- HTML 列表：先把页面下载下来用选择器试匹配，注意国内站点常用 GBK 编码（当前 HttpClient 只按 UTF-8 解码，遇到乱码需先补 iconv 能力的 adapter 变体）。

### 6.3 情形 C：需要新适配器（上游是特殊协议/签名）

1. 在 apps/server/src/collectors/ 新建 kebab-case 文件，实现 CollectorAdapter（参考 github-advisories.ts）；
2. 用 zod 定义 ConfigSchema，每个字段带 .catch 默认值；
3. 只返回 RawItem，不写库；单条失败 warnings.push，整体失败抛 UPSTREAM_ERROR（upstreamError 来自 infra/errors.ts）；
4. 在 collectors/index.ts 的 ADAPTER_INSTANCES 注册（Record<AdapterId, CollectorAdapter> 类型会强制你补齐，漏注册直接编译报错）；
5. 在 packages/shared/src/domain.ts 的 ADAPTER_IDS 与 ADAPTER_LABELS 增加枚举值（属于 shared 变更，必须先通知 Lead，由 Lead 改 shared）；
6. 写测试：优先"配置解析 + 字段映射"的纯函数测试（可用假 http 返回固定 fixture）；LIVE 测试追加到 collector.live.test.ts 的 LIVE_CASES；
7. 更新 docs/04 §3 与 §5，并在 seed 里登记至少一条数据源。

### 6.4 接入检查清单

- [ ] externalId 是否稳定（同一内容两次采集必须一致）？
- [ ] 是否只返回最近 N 天内容（防止首次接入灌历史）？

- [ ] 摘要是否清洗掉了 HTML 与超长正文？
- [ ] 是否在 docs/04 §5 与 seed 中登记？

## 7. 反爬、限流与合规

### 7.1 工程侧

- **单源失败隔离**：适配器抛错只影响该源（orchestrator 记 last_error / failure_count），其他源照常采集；
- **退避重试**：HttpClient 对 429/5xx/网络异常做指数退避 + 抖动，并尊重 Retry-After；
- **串行 + sleep**：所有适配器内部串行请求，禁止 Promise.all 并发打同一上游；
- **统一 UA**：Knetsec_Ai/1.0 (security-intelligence-collector)，部分站点（GitHub/NVD）拒绝空 UA；
- **响应体上限**：HttpClient 默认 8MB 上限，防止异常大文件打爆内存（KEV 清单 1.8MB 在限内）；
- **不绕反爬**：403/521/验证页一律标记失败并在面板可见，不实现 UA 伪装、Cookie 伪造、打码识别。

### 7.2 合规侧（docs/00 §1.3）

- 只聚合**公开披露**信息，不采集需登录内容，不绕付费墙；
- 只存**标题 / 摘要 / 链接**，正文指向原文，报告注明来源，不全文转载；
- 对 PoC 只保留链接与描述（exploit-db 源仅取标题+链接+日期），不存储可直接武器化的攻击代码；
- 不采集个人隐私数据；国内站点（CNVD/CNNVD）遵守其访问条款，默认停用。

## 9. 故障排查手册

### 9.1 症状 → 原因 → 处理

| 症状（面板 last_error / 日志） | 最可能原因 | 处理 |
|---|---|---|
| HTTP 429 / rate limit | 未配置 Token 或请求过密 | 配 GITHUB_TOKEN / NVD_API_KEY；把 intervalMinutes 调大；减少同源并发源 |
| HTTP 403 | 站点 UA 反爬 | 配代理；换官方 RSS/API；不要改 UA 伪装（合规边界） |
| HTTP 404 | 订阅地址下线 | 到站点找新地址，改 config.url |
| fetch failed / UND_ERR_CONNECT_TIMEOUT | DNS 或 TCP 不可达（含 Akamai 边缘节点） | 配代理；cisa-kev 这类间歇源稍后重试 |
| 请求超时（aborted） | 站点首字节慢（如 Unit 42 约 20s） | 已放宽到 45s；仍超时就调大 intervalMinutes 并观察 |
| itemSelector 未匹配到任何条目 | 页面结构变更 / 返回验证页 | 开发者工具重取选择器；确认是否需要代理 |
| itemsPath 未取到条目数组 | JSON 接口结构变了 / 路径写错 | 用浏览器看实际响应，改 itemsPath 或 fieldMap |
| 条目为 0 但无错误 | 时间窗内确实无新内容（NVD 7 天无匹配关键词 / KEV 30 天无新增） | 正常现象；调大 days 或换关键词 |
| 摘要里出现 HTML 片段 | 上游格式异常（内联 SVG/注释） | 检查 normalize cleanSummary；必要时给该源加专用清洗 |
| 同一内容反复入库（重复） | externalId 不稳定（含时间戳/随机数） | 改用上游稳定 ID（CVE/GHSA/guid/tag）；标题源请确认标题规范化 |
| 报告里同一条出现两次 | 跨源去重未命中 | 检查两条的 category 是否一致、发布时间是否相差 >3 天、标题相似度是否 <0.85 |
