## 1. 架构目标与约束

### 1.1 架构目标

| 编号 | 目标 | 落点 |
|---|---|---|
| A1 | **一条命令可跑**：交付给非全栈用户长期运行 | 单进程 + 单文件 SQLite + 零原生编译依赖 |
| A2 | **可扩展数据源**：新增源不改流水线 | 适配器接口 + sources 表 + `createCollector` 注册 |
| A3 | **采集与业务解耦**：外部协议变化不外溢 | collectors 只产 `RawItem`，pipeline 负责归一化/去重/富化 |
| A4 | **前后端类型同源**：接口即文档 | `@knetsec/shared` 统一 DTO 与枚举 |
| A5 | **安全默认**：后台不裸奔 | 仅监听 127.0.0.1、JWT、scrypt、限流、审计、参数化 SQL |
| A6 | **故障可见可修**：上游变了能定位 | 运行日志 + 源状态 + 试采 + 结构化日志 |
| A7 | **可运维**：备份/升级/排障有手册 | 数据全部落 `data/`；Docker 与 Windows 脚本 |

### 1.2 关键约束

1. **运行环境**：Windows 10/11 为主，Node.js ≥ 22.5（推荐 24 LTS）；无 Docker 也必须能跑；
2. **数据规模**：十万级条目、单租户、单机并发 < 10，SQLite 足够；
3. **依赖约束**：禁止需要 Visual Studio 编译的原生模块（故用 `node:sqlite` 而非 better-sqlite3）；
4. **合规模块**：只聚合公开信息，只存标题/摘要/链接，不碰武器化内容；
5. **兼容**：Linux/Docker 可选支持，但 Windows 是验收基线。

### 1.3 架构驱动因素排序

`可交付性/可运维性 > 数据源可扩展性 > 安全 > 性能 > 分布式扩展性`。这一排序直接解释了后文的取舍：不引入 Redis/MQ/PostgreSQL，不拆微服务，不引入 GraphQL，前端不拆多应用。

## 2. 架构风格与分层

### 2.1 总体风格

采用 **模块化单体（Modular Monolith）** + **端口-适配器（Ports & Adapters / 六边形）** 的混合风格：

- **单体**：一个 Fastify 进程同时托管 API、静态面板、调度器与采集流水线——部署最简单，事务边界最清晰（SQLite 单库）；
- **模块化**：按业务域拆 `modules/{auth,items,sources,tasks,reports,stats,settings,audit,system}`，每个模块内部再分「路由 → 服务 → 仓储」，模块间只经服务层调用，不跨模块直接查表；
- **端口-适配器**：采集侧定义 `CollectorAdapter` 端口，10 个适配器是可替换的适配器；HTTP 侧定义 `CollectorHttpClient` 端口，生产用 undici、测试可用桩；DB 经 `Db` 封装，业务不直接持有 `DatabaseSync`。

选择理由：本产品的复杂度在「外部数据源多、协议杂」而非「并发与团队规模」，微服务只会把 SQLite 事务拆碎、把部署复杂化；而模块化单体可保留拆分余地（未来若换 PostgreSQL，只需替换仓储层）。

### 2.2 分层视图

```

│  views / components / layouts / stores / router / api/client.ts     │
```

### 2.3 依赖规则（必须遵守）

1. 依赖方向**单向向下**：web → API 契约（shared）→ 领域 → 基础设施；禁止 infra 反向依赖 modules；
2. `packages/shared` **零运行时依赖**，只含类型、枚举、常量与纯函数常量表，可被浏览器直接打包；
3. collectors **不得** import db / modules / report：只依赖 shared 的 `CollectorContext` 与 infra/http；
4. modules 之间通过 service 调用，**禁止**跨模块直接写别人的表（审计通过 `audit` 服务统一写入）；
5. 所有 SQL 只在模块仓储/流水线内出现，路由层不写 SQL；
6. 浏览器端禁止调用 `/auth/login` 以外不带 token 的接口（健康检查与文档除外）。

## 4. 启动、调度与数据流

### 4.1 冷启动时序（`index.ts`）

```
进程启动
  │
  ├─1. config 装载：读 .env、确定 DATA_DIR、JWT 密钥（无则生成并写 data/.jwt-secret）
  ├─2. ensureRuntimeDirs()：创建 data/、data/reports/、data/logs/
  ├─3. openDatabase(config.dbPath)：打开 SQLite，PRAGMA WAL / foreign_keys / busy_timeout
  ├─4. migrate(db)：建 schema_migrations，按版本顺序执行未应用迁移（单事务）
  ├─5. seed(db)：无用户→默认管理员；无源→写入默认源；缺设置→写默认设置（幂等）
  ├─6. buildApp({ db, ... })：注册插件、鉴权、限流、路由、错误处理、静态托管
  ├─7. scheduler.start()：注册采集扫描（每 5 分钟）、报告、清理任务（KNETSEC_SCHEDULER=off 跳过）
  ├─8. app.listen({ host: config.host, port: config.port })
  └─9. 注册 SIGINT/SIGTERM：scheduler.stop() → app.close() → db.close() → 退出
```

**为什么启动时自动迁移与种子**：交付对象是非全栈用户，多一步「跑迁移命令」就多一个失败点；迁移与种子都设计为幂等，重复启动安全。

### 4.2 采集运行时序（手动或定时触发）

```
调用方（POST /tasks/fetch 或 scheduler）
   │
   ▼
CollectPipeline.run(runId, sourceKeys?)
   │ ① 读取目标源（enabled=1，按 priority；指定 sourceKeys 时校验存在）
   │ ② 创建/复用 fetch_runs：status=running、started_at；写首行日志
   │ ③ 内存锁 + DB 检查：已有 running → 拒绝并发（409 / 跳过）
   │ ④ 逐源执行（限并发 2）：
   │      for each source:
   │        ctx = { source, now, logger, http, settings, secrets }
   │        result = createCollector(adapter).fetch(ctx)      ← 超时/重试/代理
   │        if 抛错 → 记 failure、source.last_error、logs.push，不影响其他源
   │        else → pipeline.normalize(result.items, source, now)
   │                 → dedupeWithinBatch()（批内 uid/标题）
   │                 → 库内去重（uid 冲突 + 跨源相似度）
   │                 → enrich()（CVSS/KEV/标签/importance/可选 LLM）
   │                 → 单事务批量 INSERT（ON CONFLICT DO NOTHING）
   │        更新 source：last_run_at/last_status/success_count/failure_count
   │ ⑤ 汇总：sources_ok/failed、items_new/duplicate；status = success|partial|failed
   │ ⑥ 若通知开启且有 critical/KEV 新增 → 异步发 Webhook（失败只记日志）
   │ ⑦ 更新 fetch_runs：finished_at、计数、logs（单行 ≤1000）
   │ ⑧ 释放内存锁
```

**并发与幂等**：

- 同一时刻只允许一个采集运行：内存布尔锁 + `fetch_runs.status='running'` 双重检查；进程崩溃后残留 running 记录在启动时标记 failed（避免永久锁死）；
- 适配器幂等：externalId 稳定，重复采集只产生重复条目，由 uid 唯一约束与去重拦截；
- 单事务提交：一批条目一次事务，减少 WAL 写放大与锁等待。

### 4.3 报告生成时序

```
POST /reports/generate
  │ 校验 type/periodStart/periodEnd/itemIds（缺省按类型推断区间）
  │ 查询区间条目（settings.reportSections 决定章节；按 severity/importance 排序）
  │ 渲染 Markdown：标题 + 速览 + 各章节（表格/列表）+ 统计
  │ 渲染 HTML：内联 CSS、单文件、可打印
  │ 生成目录名 <id>-<type>-<yyyyMMdd>（先插入 reports 拿 id，再落盘，失败回滚记录）
  │ 写 reports 表（markdown/html/file_path）
  │ 写审计（report_generate）
  ▼
返回 { id, title, itemCount, ... } → 面板跳预览
```

### 4.4 请求处理时序（以列表查询为例）

```
浏览器 axios ──▶ Fastify
  ├─ onRequest：requestId 生成、耗时计时、安全响应头
  ├─ preHandler：JWT 校验（除白名单）→ req.user = { id, username, role }
  ├─ 路由 handler：参数校验（schema/手写）→ service 组装 SQL 参数 → db.all（命中索引）
  ├─ 序列化：JSON 数组字段解析（tags/cve_ids/ghsa_ids）、布尔转换（0/1）
  └─ 响应：{ success:true, data:{ items, page, pageSize, total, totalPages }, requestId }
异常：AppError → 统一错误处理 → { success:false, error:{code,message}, requestId }（隐藏堆栈）
```

### 4.5 数据库写入路径

| 写入者 | 表 | 事务策略 |
|---|---|---|
| 采集流水线 | items、fetch_runs、sources | 每源一批 items 单事务；运行统计最后一次更新 |
| 报告生成 | reports | 插入记录与落盘顺序一致，失败清理半成品 |
| 设置/源/用户/审计 | settings、sources、users、audit_logs | 各自小事务；写操作与审计同一请求内完成 |
| 每日清理 | items、fetch_runs | 分批 DELETE（每批 1000），避免长事务 |

### 5.3 数据库设计原则

1. **WAL + busy_timeout=5000**：读不阻塞写，短时锁等待自动重试；
2. **不用 SELECT ***：明确列名，减少 I/O 与字段漂移风险；
3. **JSON 数组存 TEXT**：SQLite 无数组类型，tags/cve_ids/ghsa_ids 存 JSON，service 层统一解析；
4. **迁移只追加**：已发布迁移不可改，新增字段走新版本；
5. **冗余快照字段**：source_name、username 冗余，保证历史可读；
6. **时间统一 ISO 8601 UTC 字符串**：可直接字符串比较排序，跨时区无歧义。

## 6. API 设计原则

### 6.1 资源与版本

- 前缀 `/api/v1`，版本进路径，破坏性变更升 v2；v1 内只做向后兼容的字段追加；
- 资源命名用复数名词（`/items`、`/sources`、`/reports`），动作型操作以子路径表达（`/sources/:id/toggle`、`/tasks/fetch`、`/reports/generate`）；
- GET 幂等可缓存（不缓存敏感响应）；POST 创建/触发；PATCH 局部更新；PUT 全量替换（settings 语义为合并，文档注明）；DELETE 删除。

### 6.2 信封与错误

```jsonc
// 成功
{ "success": true, "data": { }, "requestId": "req-..." }
// 失败
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "参数 pageSize 不能超过 100", "details": null }, "requestId": "req-..." }
```

错误码固定 8 种（与 shared `API_ERROR_CODES` 一致）：VALIDATION_ERROR(400)、UNAUTHORIZED(401)、FORBIDDEN(403)、NOT_FOUND(404)、CONFLICT(409)、RATE_LIMITED(429)、UPSTREAM_ERROR(502)、INTERNAL_ERROR(500)。业务异常统一抛 `AppError`，全局错误处理器转换；未预期异常记 `error` 日志并返回 INTERNAL_ERROR（不泄露堆栈）。

### 6.3 分页、筛选、排序

- `page` 从 1 开始，`pageSize` 默认 20、上限 100；返回 `{ items, page, pageSize, total, totalPages }`；
- 筛选参数全部显式声明类型与枚举；未知参数忽略而非报错（宽松兼容）；
- 排序字段白名单（published_at/fetched_at/severity/importance），方向 asc/desc，字段名绝不拼进 SQL（白名单映射到列名）；
- LIKE 查询转义 `%`、`_`、`\\`。

### 6.4 鉴权与限流

- 公开端点：`POST /auth/login`、`GET /health`、`GET /api/v1/health`、`GET /docs`、`GET /openapi.json`；
- 其余需 `Authorization: Bearer <JWT>`；写端点额外要求 role=admin；
- 限流：仅登录路由启用（5 次/分/IP，`@fastify/rate-limit` 配置 `global:false`），429 信封统一；其余接口依赖 JWT + 默认仅本机监听；
- JWT 负载只放 `sub/username/role/iat/exp`，不放敏感信息；12 小时后过期，前端 401 自动跳登录。

### 6.5 输入校验与契约

- 路由层用 JSON Schema（Fastify）或手写 `assert` 校验：类型、枚举、长度、数值范围、数组上限；
- 所有 DTO 来自 `@knetsec/shared`，前端不重复定义类型；
- 变更流程：先改 shared → 更新《09》→ 前后端同步构建；Swagger 由路由 schema 生成，保证 `/openapi.json` 与实现一致。

### 6.6 幂等与副作用

- 采集触发：并发保护（409）；重复点击不会产生两条 running 记录；
- 批量操作：幂等（标记已读重复执行结果一致）；
- 报告生成：非幂等（每次一条记录），前端防重提交；
- 试采：无副作用（不写库）。

## 7. 安全设计

### 7.1 认证与会话

```
登录：username + password
  → 查 users（参数化）
  → verifyPassword(scrypt)：格式异常/不匹配均返回 false（不区分原因）
  → 成功：更新 last_login_at、写审计、签发 JWT（HS256，12h）
  → 失败：统一 401 文案、写审计、计入限流
JWT 校验钩子：解析 Authorization → 验签/过期 → 查用户仍存在且角色有效 → req.user
```

- 密码哈希：Node 内置 scrypt，N=16384/r=8/p=1，16 字节随机盐，64 字节输出，格式自描述便于未来升级参数；比对用 `timingSafeEqual`；
- 密码强度：≥ 8 位且含字母与数字；默认管理员 `must_change_password` 由种子控制，面板提示改密；
- JWT 密钥：`KNETSEC_JWT_SECRET`（≥16 字节）> `data/.jwt-secret` > 自动生成 48 字节随机并 0600 落盘；密钥不写日志、不入库。

### 7.2 授权

- 全局 `onRequest`/preHandler 鉴权钩子，白名单公开端点；
- 路由级 `requireAdmin`：所有写接口（POST/PATCH/PUT/DELETE 除登录/改密）强制 admin；
- 服务层再校验一次资源归属/状态（防御式，避免路由漏挂）；
- 前端按角色隐藏按钮仅提升体验，不作为安全边界；viewer 直接构造请求由服务端 403。

### 7.3 注入与 XSS

| 面 | 措施 |
|---|---|
| SQL 注入 | 100% 参数化（`Db.run/get/all/scalar`）；排序字段白名单；LIKE 通配符转义；禁止字符串拼接 SQL |
| XSS（面板） | Markdown 渲染 marked + DOMPurify；禁止 v-html 渲染未消毒内容；CSP 响应头限制脚本源 |
| XSS（报告） | 报告 HTML 由服务端模板生成，内容对用户标题做 HTML 转义；单文件无外部脚本 |
| 路径穿越 | 报告下载只按 reports.id 查库取内容，不拼接用户路径；静态资源由 Fastify 静态插件限定 root |
| SSRF | 采集 URL 来自管理员配置，属可信输入；仍限制协议 http/https 与响应体上限，不做任意 URL 代理 |
| 请求走私/大包 | Fastify bodyLimit 2MB；采集响应体上限 8MB |

### 7.4 限流与审计

- 登录限流：内存滑动窗口（5 次/分/IP），超限 429；多实例部署时需外部限流（v1.0 单机可接受）；
- 审计动作清单（实际实现）：`auth.login`、`auth.change_password`、`items.mark_read`/`mark_unread`/`star`/`unstar`/`delete`、`source.create`/`update`/`delete`/`enable`/`disable`/`test`、`tasks.fetch`、`report.generate`、`report.delete`、`settings.update`；登录失败只写应用日志，单条情报状态更新不写审计（批量操作写）。
- 审计内容：username、action、target、detail（JSON，不含明文密钥/密码）、ip、created_at；查询仅 admin。

### 7.5 敏感信息与日志

- 日志 pino redact：password、token、authorization、llmApiKey；
- 设置接口：`llmApiKey` 脱敏（前 4 + `****` + 后 4），空值提交表示保持；
- .env、data/ 加入 .gitignore；data/.jwt-secret 权限 0600；
- 报告与面板不展示 GitHub Token / NVD Key（仅存在环境变量）。

### 7.6 网络安全与部署加固

- 默认 `KNETSEC_HOST=127.0.0.1`，禁止默认监听 0.0.0.0；
- 公网访问要求：反向代理（nginx/Caddy）+ TLS + 强密码 + 防火墙白名单（详见《06》§9）；
- 安全响应头：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy`、CSP（生产）；
- CORS 白名单默认 `http://127.0.0.1:5173`（开发），生产同源无需 CORS。

## 8. 可观测性设计

### 8.1 日志体系

| 层 | 实现 | 内容 |
|---|---|---|
| 应用日志 | pino（生产 JSON / 开发 pino-pretty） | 启动、迁移、调度、请求、采集、报告、异常 |
| 请求日志 | Fastify onRequest/onResponse 钩子 | method/path/status/耗时/requestId/用户 |
| 运行日志 | `fetch_runs.logs` JSON 数组 | 每源开始/完成/warnings/失败原因，面板可查 |
| 审计 | `audit_logs` | 写操作留痕，独立于应用日志 |

关键结构化字段：`sourceKey`、`runId`、`adapter`、`count`、`durationMs`、`status`、`err`；日志中禁止拼接密码/token/Key。

### 8.2 健康检查与系统信息

- `GET /health`：内部执行 `SELECT 1` + 进程 uptime + 版本；数据库异常时抛错返回 500（当前实现不返回 503，`db` 字段固定 `ok`）；用于 Docker HEALTHCHECK 与运维脚本；
- `GET /api/v1/system/info`：版本、环境、启动时间、运行时长、库文件大小、items/sources 数量、调度器状态；只读需登录。

### 8.3 运维可观测指标（手工/日志）

```
采集：run 状态、每源成功/失败数、items_new/duplicate、耗时
报告：生成次数、条目数、失败率
接口：请求量、5xx 数、P95 耗时（日志统计）
容量：库文件大小、WAL 文件大小、条目总量
```

> v1.0 不引入 Prometheus/Grafana：单机十万级数据用日志与 `/system/info` 足够；未来若需监控，可直接在 onResponse 钩子加 metrics 端点（已预留 requestId/耗时字段）。

### 8.4 排障路径

| 现象 | 排查顺序 |
|---|---|
| 面板打不开 | 进程是否存活 → 端口是否占用 → /health → 日志 |
| 登录失败 | 用户是否存在 → 密码哈希格式 → 限流是否触发 → 审计 |
| 没采到数据 | /tasks/status 是否到期 → /sources 的 last_error → 试采 → 代理/Token → 上游可达性 |
| 重复条目 | uid 生成逻辑（externalId 是否稳定）→ 跨源阈值 → 源优先级 |
| 报告缺失章节 | 区间内是否有该分类条目 → settings.reportSections |

## 9. 扩展性设计

### 9.1 新增数据源（最常见扩展）

步骤固定为 4 步，**不改流水线**：

1. 新建 `apps/server/src/collectors/<name>.ts`，实现 `CollectorAdapter`（`id` + `fetch(ctx)`），校验并补全 config 默认值；
2. 在 `collectors/index.ts` 的 `createCollector` 注册分支；
3. 在 `seed/sources.seed.ts` 增加默认源（key/name/category/adapter/config）；
4. 补一个适配器单测（用固定 JSON 样例断言字段映射），并在《04》登记可达性与配置说明。

若只是「换一个 RSS/JSON/HTML 站点」，无需写代码：管理面板直接新增源并选对应通用适配器。

### 9.2 新增通知渠道

1. `packages/shared/src/domain.ts` 的 `NOTIFICATION_CHANNELS` 加值 + 中文标签；
2. 服务端通知模块加报文模板分支；
3. 设置页渠道下拉自动出现（前端读常量）；
4. 更新《09》与《02》对应需求。

### 9.3 新增业务模块 / API

按 `modules/<domain>/{routes,service,repo}.ts` 三件套落地，在 `app.ts` 注册前缀；DTO 先加 shared；迁移新增表/字段另起版本。禁止在既有模块里塞跨域逻辑。

### 9.4 存储与部署扩展

| 场景 | 方案 |
|---|---|
| 条目量 > 50 万、查询变慢 | 归档旧数据（按年分库）或加 FTS5 虚拟表做全文检索 |
| 多实例/高可用 | 换 PostgreSQL（repository 层已隔离 SQL），调度器改为单实例选主或外部 cron |
| 公网多用户 | 引入 OIDC/SSO、按角色的数据权限、审计外发 |
| 采集规模扩大 | 采集任务改为队列 + worker（BullMQ），保持适配器接口不变 |

> 这些是预留路径，不是 v1.0 范围；设计上通过「端口-适配器 + repository 隔离」保证未来替换成本可控。

## 10. 技术选型对比与取舍

### 10.1 后端语言与框架

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Node 24 + TS + Fastify 5**（选用） | 内置 fetch/node:sqlite/loadEnvFile；前后端同语言共享类型；启动快、依赖少 | CPU 密集场景弱（本项目无） | ✅ 选用 |
| Python + FastAPI | 生态好、解析库丰富 | 本机 Python 3.8.6 过旧；升级污染环境；需 venv/依赖编译 | ✗ |
| Go + Gin | 单二进制、性能好 | 学习/维护成本高；与本机既有 Node 生态不匹配；SQLite 需 cgo | ✗ |
| NestJS | 结构规范、DI | 抽象层重、启动与调试成本高，单机小项目过度设计 | ✗ |
| Express | 生态最大 | 校验/日志/OpenAPI 需自行拼装；性能与错误处理弱于 Fastify | ✗ |

### 10.2 数据库

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **SQLite + node:sqlite**（选用） | 零运维、单文件、免原生编译、WAL 并发读、备份=复制文件 | 单写者；不适合多实例 | ✅ 十万级+单机完全够用 |
| better-sqlite3 | API 成熟、性能略好 | Windows 需 VS 生成工具编译，首次安装易失败 | ✗ |
| PostgreSQL | 并发强、功能全 | 需要安装/运维服务，违背「一条命令可跑」 | ✗ |
| MongoDB | 无模式 | 查询/统计/事务不如 SQL 直观；额外服务 | ✗ |

### 10.3 其他选型

| 能力 | 选用 | 对比与理由 |
|---|---|---|
| 调度 | **croner** | 支持秒级、时区、无原生依赖；node-cron 时区支持弱，bullmq 需 Redis |
| HTTP 客户端 | **undici**（Node 内置同源） | 支持 ProxyAgent、连接池、AbortSignal；axios 客户端场景更重 |
| XML/Atom 解析 | **fast-xml-parser** | 纯 JS、快、无原生依赖；xml2js 更慢 |
| HTML 解析 | **cheerio** | jQuery 风格、容错好；正则解析不可维护 |
| 前端 | **Vue3 + Vite + Element Plus** | 后台表格/表单/抽屉完备、中文文档好；React+AntD 亦可但团队交付习惯 Vue |
| 图表 | **ECharts** | 趋势/饼图开箱即用、中文生态；Chart.js 功能较弱 |
| 状态/路由 | **Pinia + Vue Router 4** | 官方推荐组合，类型友好 |
| 测试 | **Vitest 3** | 与 Vite 同源、快；Jest 配置与 ESM 支持更繁琐 |
| 日志 | **pino** | 最快的 Node 结构化日志之一；winston 更重 |
| 校验 | Fastify JSON Schema + 手写 | 少一个依赖；zod 虽类型好，但 schema 已够用（采集器 config 手写校验） |

### 10.4 关键取舍

1. **不做微服务**：数据量、并发、团队规模都不支持，微服务只会把 SQLite 事务拆碎；
2. **不做前后端分离部署**：生产由 Fastify 直接托管 `apps/web/dist`，少一个 nginx 依赖；需要时 Docker Compose 提供 nginx 反代；
3. **不做全文检索**：LIKE + 索引满足十万级；FTS5 作为未来扩展；
4. **不做实时推送**：轮询刷新 + 定时采集足够，省掉 WebSocket 连接管理；
5. **不用 ORM**：手写参数化 SQL 更透明、可控、易审计（表少、查询简单）。

## 11. 性能与容量设计

| 设计点 | 做法 | 收益 |
|---|---|---|
| 索引覆盖 | 列表高频条件建联合索引；`ORDER BY published_at DESC` 走索引 | 万级列表 P95 < 300ms |
| 分页上限 | pageSize ≤ 100；导出单独上限 5000 | 防大结果打爆内存 |
| 聚合查询 | 仪表盘用 `COUNT`/`GROUP BY` + 时间条件，避免全表 | P95 < 500ms |
| 批量入库 | 每源一批单事务 + prepared statement 缓存 | 减少 WAL 写放大与锁等待 |
| 采集并发 | 源间限并发（2），单源内串行 | 兼顾速度与上游限流 |
| HTTP 复用 | undici Agent keep-alive、连接池 16 | 降低 TLS 握手开销 |
| 大响应保护 | 响应体上限 8MB、请求体上限 1MB | 防异常上游/恶意请求 |
| 静态资源 | 生产由 Fastify 静态托管 + 浏览器缓存头 | 首屏快 |
| LLM 可选 | 默认关闭；开启后 20s 超时跳过 | 不拖慢主流水线 |

### 11.4 容量与压测假设

| 假设项 | 取值 | 依据 |
|---|---|---|
| 单实例接口并发 | 5-10 请求/秒 | 单运营 + 少量只读用户，无公网高并发 |
| 单次采集条目 | 每源 20-100 条 | 适配器只取最近 30 天，NVD 只取 7 天窗口 |
| 单次报告素材 | ≤ 2000 条 | 报告服务硬上限，避免渲染内存峰值 |
| 数据库年增长 | 约 10 万条 / 100-200 MB | 去重后日均 100-300 条，保留 180 天 |
| 停机备份窗口 | < 5 分钟 | 复制 data 目录（库 + 报告 + 密钥） |
| 冷启动时间 | < 5 秒 | 迁移 + 种子 + 监听，空库实测秒级 |

### 11.5 性能瓶颈与优化顺序

1. **上游限流等待**（最常见）：采集耗时主要花在 GitHub/NVD 的限流与网络等待上，不是 CPU；优化手段是 Token、窗口裁剪、并发上限，而不是加机器。
2. **SQLite 写锁**：批量入库集中在一个事务里提交，避免每条一次 fsync；读多写少的接口走 WAL 不受影响。
3. **报告渲染**：Markdown/HTML 拼接是字符串操作，2000 条以内毫秒级；真正的成本是查询与数据装载，已用索引 + LIMIT 控制。
4. **前端大表格**：列表分页上限 100，导出走独立接口并限制 5000 条，避免浏览器一次性渲染上万行。
5. **备份/清理**：备份是文件复制，清理按天批量 DELETE，均不在请求链路内。

> 优化原则：先确认瓶颈在「上游、数据库还是渲染」，再动手；本项目在单机十万级数据下，瓶颈通常不是应用代码。

### 11.6 架构决策记录（ADR）

| 编号 | 决策 | 背景 | 理由 | 影响 |
|---|---|---|---|---|
| ADR-01 | 模块化单体而非微服务 | 单机交付、单租户、团队规模小 | 事务边界清晰、部署简单、无网络调用开销 | 未来拆服务需先拆数据库边界 |
| ADR-02 | SQLite（WAL）而非 PostgreSQL | 用户要求一条命令可跑、零外部服务 | 免运维、备份=复制文件、十万级性能足够 | 多实例/高并发写受限 |
| ADR-03 | Node 24 + 原生 node:sqlite | Windows 无 VS 编译工具链 | 零原生编译、内置 fetch/loadEnvFile | 需要 Node ≥ 22.5 |
| ADR-04 | Fastify 5 而非 Express/Nest | 需要校验、Swagger、限流、性能 | 插件齐全、schema 与 OpenAPI 一体、开销低 | 团队需熟悉 Fastify 生命周期 |
| ADR-05 | 手写参数化 SQL 而非 ORM | 表少、查询固定、安全要求高 | SQL 透明可控、易审计、无 ORM 隐式查询 | 新增查询需手写并做参数化评审 |
| ADR-06 | Vue3 + Element Plus | 后台管理场景、中文生态 | 表格/表单/抽屉组件齐全，开发效率高 | 需控制打包体积（按需引入） |

## 12. 风险与缓解

| 编号 | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | 上游接口/页面结构变更导致适配器解析失败 | 高 | 单源失效 | warnings + last_error 可见；单测固定样例；通用适配器可在线改配置 |
| R2 | GitHub 未认证 60 次/小时限流 | 高 | 采集失败/降频 | 支持 GITHUB_TOKEN（5000 次/时）；429 指数退避；控制每源请求数 |
| R3 | NVD 未认证 5 次/30 秒限流 | 中 | 采集慢 | 支持 NVD_API_KEY；7 天窗口；失败延后重试 |
| R4 | CNVD/CNNVD 大陆网络不可达（TLS 吊销检查失败） | 高 | 国内源缺失 | 源登记默认 enabled=0；支持 KNETSEC_HTTP_PROXY；失败只记不影响整轮 |
| R5 | RSS 源 403/反爬 | 中 | 少几个媒体源 | 统一 UA、备选源、登记停用并文档说明 |
| R6 | SQLite 单写者锁等待 | 中 | 接口短时慢 | WAL + busy_timeout=5s + 短事务批量写 |
| R7 | 采集并发导致重复入库 | 低 | 数据重复 | 内存锁 + running 检查 + uid UNIQUE + ON CONFLICT DO NOTHING |
| R8 | 报告 HTML XSS（上游标题含脚本） | 低 | 面板/浏览器风险 | 服务端模板转义 + 前端 DOMPurify + CSP |
| R9 | JWT 密钥泄露 | 低 | 会话伪造 | 环境变量优先、0600 文件、不入库不写日志、可随时轮换 |
| R10 | 数据目录误删 | 中 | 数据丢失 | 文档强调备份 data/；提供备份脚本与 Docker 卷 |
| R11 | 依赖升级破坏兼容 | 中 | 构建失败 | 锁文件 + 版本固定；升级在独立 PR 验证 typecheck/test |
| R12 | 用户把 8787 直接暴露公网 | 中 | 后台被攻击 | 默认仅 127.0.0.1 + 文档安全加固章节 + 强密码提示 |
